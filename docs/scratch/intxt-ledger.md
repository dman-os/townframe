## Decisions

- **D1 (2026-11-10, operator)** One intxt is one drawer.
- **D2 (2026-11-10, operator)** Clients write intxt datums directly through the generic datum writes; no API over the datums where avoidable. The nodule only does what clients can't (design §5).
- **D3 (2026-11-10, operator, recorded by the node lane)** Nodule methods act with the capability the caller presents, never the nodule's own grants.
- **D4 (2026-11-10, operator)** GitHub sync is on the roadmap, probably not this week.
- **D5 (design discussion)** A future VCS is separate from the intxt: an intxt composes artifacts and doesn't own their histories.
- **D6 (2026-11-10, operator)** Focus is the write loop ("replacing PRs"); pure viewing is later.
- **D7 (2026-11-10, operator)** Sessions: our own normalized datums with ACP-compatible naming (O1); one doc per session, subagents as linked sessions (O2). Later option: variant sessions as Automerge forks of their parent session doc.
- **D8 (2026-11-10, operator)** Design philosophy: datums are containers/records of history. Multiplayer editing may use other datums over the same use case, but not by default.
- **D9 (2026-11-10, operator)** Work structure (tasks, decisions) is its own datums; adapters can map harness task systems (todo lists, plans) into them.
- **D10 (2026-11-10, operator)** Agent interface: MCP, CLI and hooks all eventually; the first shipped use case sets the order.
- **D11 (2026-11-10, operator)** Evidence coverage across stacks (U10) is deferred past this week; keep it enumerated.
- **D12 (2026-11-10, operator)** FDRs: one for the general system, one per shipped feature, starting with the first. FDRs describe what users do, and users include harness adapters, GitHub, agents, humans and supporting software. No reference-model internals in FDRs.
- **D13 (2026-11-10, operator)** Multiplayer is a requirement for every datum: concurrent writers must not clobber each other.
- **D14 (2026-11-10, operator)** First feature: the agent review loop (capture → phone review → agent picks up feedback → next revision), aimed at needs today's tooling serves poorly (e.g. Claude remote control shows no files or diffs).
- **D15 (2026-11-10, operator)** The intxt graph is over arbitrary datums, not filesystem-first. A reference is a datum ref pinned at heads plus a selector into that datum; nothing more is needed in the core. Code (file docs), git/jj objects, sessions, guides and CI results are all just datums. Supersedes the multi-kind `Target` union in `intxt-design.md` §3.
- **D16 (2026-11-10, operator)** No VCS units in the intxt. intxt and a future VCS may have separate change units. "Logical change" (O5) is not a v0 concept; grouping is a structure datum with several references.
- **D17 (2026-11-10, operator)** Git/jj objects are imported as datums (commits; jj op log objects if needed). All observed commits are kept; a separate ref/bookmark datum points at a commit, and walking parents from it visits only reachable commits. No predecessor links: the ref datum's own Automerge history records what it pointed at before (a reflog for free), which gives revision-to-revision pairing.
- **D18 (2026-11-10, operator)** No verdicts in the alpha: intxt isn't managing trunks, so approve/request-changes vocabulary waits.
- **D19 (2026-11-10, operator)** Agent interface order: harness hooks + CLI first, MCP after.
- **P1 (2026-11-10, closed 2026-11-10: superseded by D29/D32, single-writer worktree docs removed and replaced per doc) (proposal, not settled; operator unsure it solves the problem; expand in ADR A3)** Unmoored work goes into a private local working set of docs; intxts are made from it afterwards. The footgun it addresses: Automerge can't unsync changes, so moving work out of an intxt is a revert, not a reset, and shared genesis history follows a doc wherever it goes. Rebuilding docs with synthetic history to shed unrelated changes is not an optimisation to tackle now. This is the main cost of the reference model.
- **P2 (2026-11-10, closed 2026-11-10: superseded by D26, then D29)** The working log as a local branch of the file doc (ADR 007 `BranchDoc`/`MergeDoc`, implemented): capture writes per-edit changes to a private, unsynced branch; promotion merges it (keeping per-edit provenance natively); broken or unwanted work is discarded by not merging, or by merging only up to chosen heads (a prefix). Constraints found: a merge carries every intermediate state (junk or secrets) with it, so the only way to drop a middle state is a squash replay; a branch needs its origin doc to exist, so work recorded before any intxt needs a root doc, and a per-repo root shared by several intxts reintroduces shared genesis (P1). Operator wants a usable default, not knobs. Also considered: the day node watching the checkout continuously like Delta's `worktree mount` (delta-claude source: hooks record only the conversation; files sync through a separate mount process).
- **D26 (2026-11-10, operator)** Git commits are the base layer; intxt does not do its own version control. File docs follow refs, not the working tree: written only when a tracked ref moves, never on checkout, staging or working-tree edits. Intermediate edits stay as patches in session docs. Live per-edit file tracking is a separate future doc kind (editor/LSP integration). An intxt may track several refs, so one path may have several file docs (one per ref). Two machines recording independently make two intxts. Supersedes P2 for code. Ingestion is deterministic in content but each writer is its own Automerge actor; no actor-id tricks to make concurrent ingestion converge (operator), P3's read-at-pins rule handles it.
- **P3 (2026-11-10, closed 2026-11-10: moot under single-writer worktree file docs, ADR 040)** Multi-writer file docs without a winner: (1) file content is always read at a commit's pinned heads, never at "current"; (2) a writer splices from the doc's actual current text to the commit's content, never from its own last write, so a concurrent splice by another machine is transient and the next write repairs it; (3) concurrent moves of one ref conflict on `gitRef.target` and both `refMove`s stay, shown as a divergent ref until the next move (jj's conflicted bookmark); (4) which doc holds a ref's path is a datum slot; if two machines create one concurrently, the loser's doc stays readable through its own commit datums, only future writes go to the winner. A new ref whose base commit is already in another ref's file doc branches from it (ADR 007) so cursors carry. Merges: file set is the paths changed between merge-base(base, tip) and tip (GitHub's three-dot "files changed"), so merging the base in adds no file docs.
- **D21 (2026-11-10, operator)** The intxt is the package; its member docs may come from other apps or contexts, pinned from the global doc space as drawers do. A session spanning two intxts is one session doc in both; how much of it each intxt shows is a viewer concern, not a storage one.
- **D22 (2026-11-10, operator)** No injection and no interruption: steering is the harness's concern. intxt is a two-way protocol at the datum level (the agent reads feedback datums and writes replies), but this alpha implements a passive recording loop, not a driver loop. An agent can set up its own wake script if it wants. A full agent harness is on the roadmap and could later merge with this at the datum level. Supersedes FDR 007 step 6's adapter-delivered feedback.
- **D23 (2026-11-10, operator)** An agent reads an intxt like any document and authors it by manipulating datum JSON directly; no special feedback API for now (a convenience can come later). The datum design has to be good enough for that.
- **N2 (2026-11-10)** dpaths leaves "named collections of changes" open: FDR 003 calls a cross-document timeline row presentation, not an atomic multi-document commit, and FDR 004 Q4 asks whether cross-document correlation markers for `db commit -m` are worth it. intxt's commit/revision datum (a map of doc → heads plus metadata) is exactly such a marker. It is a datum, not an Automerge feature, and could serve dpaths too.

- **N3 (2026-11-10) `+` in a URL scheme parses fine everywhere tested**: Chromium 156, Firefox 158, Node 24 (ada) and Deno all accept `db+datum:/<doc>/<tag>/<slot>` per the WHATWG URL Standard (scheme = alpha then alphanumerics, `+`, `-`, `.`), giving protocol `db+datum:`, empty host, the full path, and `#…` as the fragment. A `//` after the scheme (`db+datum://zDoc/…`) makes the doc id a host, so the single-slash form is the one to keep. Safari not tested here. Test page: scratchpad `urltest.html`.

- **N4 (2026-11-10) Automerge already has a sub-document URL grammar** (automerge-repo main, `AutomergeUrl.ts` and `src/subdoc-handles/{types,parser}.ts`; release not yet identified, read through a summarizing fetch, so verify against source before relying on details): `automerge:<docId>[/<path>][#<heads>]`. Heads go in the fragment, `|`-joined, each bs58check, sorted. Path segments are `/`-separated, empty segments rejected: `@N` is a list index, `{json}` is a match on a list element's fields (URL-encoded, sorted keys), `[start-end]` or `[cursor]` is a text cursor range, and anything else is a URL-encoded map key (keys starting with `@ { [ \\` are escaped with `%5C`). The Rust `automerge` 0.11 crate defines no URL, only the cursor string form `s` | `e` | `[-]<counter>@<actorHex>`. Implication for A1: our selector-into-datum can adopt this path grammar (and heads-in-fragment) instead of inventing one; the divergence is the datum layer (tag + key slot) above Automerge paths.

- **N5 (2026-11-10) How datum references encode slots today, and the problems** (`big_cabinet_core/reference.rs`): a slot is bytes. `DatumKey`'s string form is `tag/` + the slot as a Go string-literal body (printable Unicode kept, `\\xNN` for invalid bytes). The URI form then percent-encodes that string but leaves `/` raw, so the slot runs to the end of the path: `db+datum:/self/org.example.note/quote%5C%22…` (double escaping: `"` → `%5C%22`). Problems I should have flagged earlier: (1) slots containing `/` make the slot unbounded, so nothing can follow it, and a selector path can't be appended without ambiguity; (2) the leading `/` makes the path hierarchical, so WHATWG parsers normalize dot segments (`new URL("db+datum:/zDoc/tag/../x").pathname` is `/zDoc/x`), which is why the code must reject `.`/`..`; without the leading slash the path is opaque and isn't normalized (tested in Node), as with `automerge:<docId>/<path>`; (3) Correction (2026-11-10): Go escaping is not redundant. It exists because Automerge map keys must be valid Unicode strings while slots are bytes; the escaped `DatumKey` string IS the Automerge key (`docs/wiki/docs.md`: slots are expected to be UTF-8, Go literal escapes for non-UTF-8 values; no recorded reason for choosing Go's format specifically, beyond a specified reversible spelling with published vectors that leaves UTF-8 untouched). The URL should therefore percent-encode the stored key string, exactly as automerge-repo encodes any map key, rather than re-encode raw bytes. Datums are stored at `ROOT/"datums"/<DatumKey string>` (`big_cabinet/doc.rs`), so a datum is literally an Automerge map path.

- **N6 (2026-11-10) Schemes in use and how they abuse `+`.** Occurrences in src/docs/x: `db+facet:` 124 (older name of datum refs: dpaths FDRs, dayledger `FacetRef`, `daybook_cli plugs` taking `db+facet://` refs), `db+datum:` 62 (`big_cabinet_core/reference.rs`, `db+datum:/<doc>/…`), `db+blob:` 40 (Kotlin app, `db+blob:///<digest>`), `db+actor:` 13 (`big_cabinet/authority/actor.rs`, `db+actor://<node key>/<path>`), `db+command:` 3 (`daybook_pdk`, `db+command:///@daybook/plabels/label-note`), `db+iroh-clone:` 2 (`daybook_cli`, `db+iroh-clone:<ticket>`). Placeholders `future+key:`/`future+blob:` appear once each. Problems: the conventional reading of `a+b:` is application protocol over transport (`git+ssh`, `svn+ssh`, `coap+tcp`), but ours is namespace + resource kind, which is inverted; and the forms disagree on authority (`:///` empty authority, `://<node>` authority, `:/` none, `:<opaque>`). Go escaping is used only for datum key slots (`reference.rs`); it escapes invalid UTF-8, `"`, `\\` and non-printable characters, i.e. it makes the key printable UTF-8, while percent-encoding makes the URL ASCII. `db` stays (operator: daybook and database; the CLI is now `day` and the daybook name is being dropped, so document it as database).

## For the ADRs

- **A1** Revised proposal (2026-11-10, after operator: a datum is not just a map value, and places that take datums must not take fields): path = the datum (the primary resource with its own semantics), query = version (`?heads=`), fragment = selector inside the datum (`#<automerge path>`). Fragments are a secondary resource interpreted by the primary's type and are excluded from resource identity (RFC 3986 §3.5; JSON Pointer fragments RFC 6901 §6; W3C Media Fragments; atproto `lex:nsid#def`), so APIs that take a datum reject a fragment; a query selecting a version follows S3 `?versionId=` / MediaWiki `?oldid=`. Diverges from automerge-repo (heads in `#`) because Automerge has no datum layer. With the field path out of the path, slots can keep raw `/` again; with no leading slash the path is opaque, so `..` in a slot is never normalized. Covers all `db+*` schemes (N6). Superseded first proposal: `db+datum:<doc>/<tag>/<slot>[/<automerge path>][#<heads>]` with no leading slash (opaque path, no dot normalization), the slot as ONE segment: the stored (Go-escaped) slot string percent-encoded with `/` as `%2F`, i.e. automerge-repo's key-segment rule (so a slot is bounded and nothing ambiguous follows it), the selector after it using automerge-repo's path grammar unchanged, and heads in the fragment as automerge-repo does. One scheme addresses both a datum and positions inside it (a datum reference is the prefix of an inside-datum reference); Rust keeps distinct types so APIs that need a whole datum reject a selector. Check: the selector addresses Automerge storage structure, so the datum codec must keep JSON structure 1:1 with storage for paths to mean the same in both. (operator 2026-11-10: check what URL parsers actually accept, browsers first: `+` in the scheme is reportedly a problem; say what `db` stands for; reuse Automerge's URL syntax, including any sub-document/field references, and diverge only where needed.) Improve the general-purpose datum reference/URL terminology and grammar. Today there are `db+datum:/<doc>/<tag>/<slot>` (ADR 007/021), the older `db+facet:///<doc>/...` still used in dpaths FDRs and the dayledger plug (`FacetRef`), sibling `refHeads`, and no selector-into-datum form. intxt's references (D15) need one coherent vocabulary: datum address, version pin, selector.
- **A1 draft (2026-11-10, operator: drop `db` and `+`; fragment approach accepted; only datum, actor and blob survive, the rest go until redesigned)**. One scheme, kind as the first segment of an opaque path, as `did:<method>:` and URNs do. Name proposed `day:` (matches the `day` CLI and daynode; IANA has no `day`, `big`, `frame`, `datum`, `tf` or `townframe` registration, checked 2026-11-10; unregistered use of `day:` not checked).
  - `day:datum/<doc|self>/<tag>/<slot>[?heads=<h>|<h>][#<automerge path>]`: path = the datum, query = version, fragment = position inside it. APIs taking a datum reject a fragment.
  - `day:actor/<node key>[/<path>]` (was `db+actor://<node key>/<path>`).
  - `day:blob/<multihash>`: content identity only. In big_blobs a reference to a blob is a reference to its `Blob` datum (digest, mime, length, and the cipherBlob found by naming convention, bytes through drawer inventories); a bare digest carries no context to fetch or decrypt, so no query hints (`?size` duplicates `lengthOctets`, `?via` is superseded by the naming convention, `?kem`/`?keyring` are withdrawn). `Blob.urls` is legacy (the encryptor no longer writes it; `big_blobs/documents.rs` still falls back to it and accepts `db+blob` and `daybook-blob`) and can be retired with daybook_core's migration.
  - Dropped until redesigned: `db+facet` (becomes datum), `db+command`, `db+iroh-clone`, `future+*` placeholders.
  - To decide: heads encoding in the query (automerge-repo's bs58check, `|`-joined and sorted, vs our hex `refHeads`); the scheme name.

## Findings

- **F1 (2026-11-10) Automerge cost of carrying source as Text** (automerge 0.11, real PRs #76 7.4 MB / #79 5.4 MB base+head of touched files; scratchpad experiment `am-exp`, single runs on a loaded machine, ±2x):
  - On-disk `save()` is 0.16–0.24× input for every variant (#76: one doc 1.2 MB, per-file docs 1.4 MB total, patch-as-Text 0.8 MB, plain Str 1.6 MB). Size is not the problem.
  - Memory and load are: one doc holding all files as Text peaks at 840 MB building and 514 MB / 7 s loading. One doc per file peaks at 160 MB building, 75 MB with all 404 loaded, 6.3 s to load all (a viewer loads only the files it shows). Plain Str loads in 0.07 s.
  - Build edits with line-diff splices; automerge's `update_text` is character-level and 25× slower (447 s vs 17 s) with 7× the patches.
  - An incremental revision (81 files edited to #77) is 345 KB; a 1% edit in 20 files is 16 KB.
  - Cursors made at rev1 resolve correctly at rev2 in 52/53 (#76) and 53/60 (#79) files; all misses are moved blocks, which a line diff expresses as delete+insert. Moves still need quote matching or a move-aware diff.
- **F2 (2026-11-10) Harness transcripts** (Claude Code, OpenCode, Pi on this machine; Codex/omp have no turn data left): conversation is ~6% of a Claude Code log; every harness with data yields per-edit unified patches; none records the commit per turn. Delta ingests transcripts as ACP session updates and files via a checkout mount; its agent does no extra annotation work.
- **F4 (2026-11-10) gitoxide on wasm32-wasip3 works with two shims** (mothership, `~/scratch/intxt-gix-wasip3`; gix 0.90, features `sha1,revision,blob-diff`; rustc 1.100 nightly; a small wasmtime 48 + wasmtime-wasi p3 host, since the dev shell's wasmtime 38 lacks component-model-async). The whole tree compiles unpatched (`sha1` is required; release wasm 3.9 MB). At runtime `memmap2` returns Unsupported on WASI (used unconditionally by gix-odb/pack/index/ref) and `filetime` hits `unimplemented!()`; `[patch]` shims fix both (memmap2 as a read-into-Vec, so whole packs land in wasm memory, a limit for big repos). On a real repo with a read-only preopen: rev-parse, commit metadata, a 57-commit range walk, a tree-to-tree diff with rename detection (668 changes, 14 renames) and 7 MB of blob reads all worked, in 0.4 ms–1.4 s each under heavy machine load. Untested: worktree status, multi-pack-index, commit-graph, linked worktrees, writes. So the intxt nodule CAN build revisions from a granted checkout (R19), at the cost of maintaining the two shims. Caveat: the agent stacked its build on another lane's (load reached ~25).
- **F5 (2026-11-10) Session import prototype** (`/run/media/asdf/p3N/tmp/intxt-proto/session-import`, outputs in `out/`): all 254 Claude Code sessions here (17 main, 237 subagent) normalize from 673.6 MB to 28.1 MB (4.2%); largest normalized session 2.67 MB (125 turns, 3,483 messages, 77 edits), main p50 408 KB. - **F6 (2026-11-10) Rebase anchor test** (`/run/media/asdf/p3N/tmp/intxt-proto/git-record`, outputs in `out/`). `chore/mbx` turned out to be a merge, not a rebase; the real sample is `stack/cabinet-06-drawer-service` (5404b01d rebased onto edfaabb5 as 0b729a1d, 4 commits, 153 files, 13 of them changed in content by conflict resolution). - **F7 (2026-11-10) Capture loop prototype** (`/run/media/asdf/p3N/tmp/intxt-proto/session-import`, `capture <hook-event>` with Claude Code hook JSON on stdin; 8 tests pass, rerun by me). - **F8 (2026-11-10) ListDatums cost and a write ceiling** (bench `doc::e2e::bench::list_datums_cost`, ignored, uncommitted in mothership `~/scratch/townframe-intxt`; release aarch64; N=100/300/1000 rerun by me). Notes of ~300 B, one slot each. ListDatums: 100 slots 104 ms, 300 → 0.91 s, 1,000 → 5.1 s, 5,000 → 25.5 s; current and historical heads cost the same; RSS flat (listing adds nothing to the loaded doc). Cause: `list.rs` calls `gate.rs` `signature_heads` per slot, which does several `get_all_at`/`length_at` at explicit heads even for `At::Current`, and each `_at` read costs time proportional to the doc, so the listing is roughly quadratic. Likely fix (not tried): read without `_at` when heads are current, or `fork_at` once for historical. **Ceiling:** updating an existing slot in a doc of ≥1,000 signed datums is refused, `BaseNotAccepted … Pending { reason: "resource limit: metadata frontier" }`, from `claim_history.rs` `account` against `HistoryBudget.max_entries_per_frontier = 1024`, which counts entries read across the frontier, not per datum. Creation still succeeds. Write cost also grows with the doc (2 ms/datum at 100, 12 ms at 1,000). Consequence for ADR 036: notes docs and session docs (largest session has 3,483 messages, F5) pass these sizes, so per-slot seen state and one-doc-per-session both depend on this being fixed in big_cabinet, or on sharding docs (notes and session docs split by count). Reported to the operator and p3N-2.
- **F10 (2026-11-10) Cabinet fixes and corrections to F8** (node lane, mothership release, not yet on feat/big-node). My F8 cause was wrong: reading at explicit heads was not it (p3N-2 tried it first, no change). The cause was `datum_version` calling `get_change_by_hash` per slot, which in automerge 0.11 re-encodes the change by scanning every op; now `get_change_meta_by_hash`. ListDatums at 100/300/1,000 slots: current 3.5/12/36 ms (was 0.10/0.98/5.2 s), historical 7/23/70 ms. Initial write of 1,000 went from 12.4 s to 5.1 s; writes are still super-linear (3,000 took 66 s). **Ceiling is ~500 datums, not 1,000:** an update's base check scans the whole `datumUuids` index for aliases, ~2 budget entries per datum against the 1,024 per-frontier bound; fix (reverse index or direct lookup) waits on the operator. Until then keep docs under ~500 datums; creates are unaffected. **Updates don't accumulate signatures:** each write replaces the signature list with one entry (`claim_history.rs:388`); 600 consecutive updates to one datum succeeded, so a per-turn datum appended on every hook is fine. **Seen state:** one map datum per reader hits `NativeReadBudget` MAX_NODES 16,384 (`dmeta/native.rs`) at ~5,400 slots (from the code, untested); use a seen datum per reader per slot range, or per slot.
- **F9 (2026-11-10) PollDatums `caught_up` is not read-your-writes** (from p3N-2, fixed test in 81b1d5ba): the poll feed is an async projection, so right after a write, a poll may answer `caught_up: true` at a cursor that excludes it. The CLI wait loop keeps re-polling with a hold; read-your-writes means looping until the written row appears.
- **F3 (2026-11-10)** `feat/dpaths` (FDR 001–003, ADR 010–012) designs checkout ingest of filesystem edits into documents (watch mode, no staging) and leaves multi-doc ingest messages to a future design: the natural hook for edit→turn provenance in the VCS stage.

- **F11 (2026-11-10, from the nodules lane, feat/big-node b2526fd3) dmeta cost and unsigned edits.** No per-write dmeta measurement exists (`big_node/e2e/costs.rs` measures whole operations, one doc per note; `big_cabinet/doc/e2e/list_costs.rs` pins ListDatums; #85 took drawer stored:saved from 205:1 to 8.4:1 and per-note node dir from 147 KB to 33 KB). They ask us to write the bench at `src/big_cabinet/doc/e2e/write_costs.rs` beside `list_costs.rs`, driving the docs service directly: allocation counts asserted, latency printed in release; byte split = edit change bytes vs save size before/after; N=500 × 1,000 edits on mothership. A full-string Text write already becomes a splice (`TextReconciler::update`). Unsigned intermediate changes: rejected today (the ADR 020 §6 gate compares the value at H with the value at the datum heads; the write path gates its base before signing; merge gates every branch key). But a signature landing on top already covers unsigned changes beneath it, so soundness needs no new verification, only a rule on who may put unsigned changes under your signature (otherwise any keyhive writer could inject content for a later signer to endorse).
