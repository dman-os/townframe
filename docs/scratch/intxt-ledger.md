## Direction (read first)

Set by the operator, 2026-11-24 (D76, D77). These outrank the older week goals (D66).

**Two frontiers, run in parallel:**

1. **Citizenship: intxt is a good citizen of the malleable universe.** intxt runs on the same mechanisms any micro or cartridge would, with no special cases in the node, the host or `day`. Whatever intxt builds that is useful elsewhere is designed to work generally: comments, recording, anchors, forge data, short ids. The intxt lane is rigorous and demanding with the lanes it depends on (nodules for the node and `day`, claytxt for micros and hosts). It asks for the general mechanism, not an intxt-shaped hole, and holds them to it.
2. **Product: the real user experience, prototyped and iterated now.** This frontier takes shortcuts so it is never blocked on claytxt or the day node. When the two frontiers conflict, product goes first. It is not a licence to be stupid: every shortcut that makes intxt special is entered in the Citizenship register below with what fixes it, and the register is worked down on the citizenship frontier.

**The principle under both** (D74): record and structure always; work out use and delivery later.

**This week (D77–D86), product goals:**
- **Review on mobile is the read-only web viewer** in a phone's browser (D86).
- Anything that changes an intxt, review included, lives in the desktop and phone app.
- Forges are deferred (D85).

The viewer's remaining work, in order:
1. A real source: read an intxt through the viewer's relay node. Until "public" exists (C11), access is a per-intxt invite of that node.
2. Hosting the relay and the viewer on the x86 box that replaces mothership (operator).
3. Commits, messages and patches from the intxt itself (VCS-agnostic): plain server-rendered diffs first, then claytxt's diff view (C12).
4. A phone-first layout, with its own Tailwind build.
5. `day x intxt show` and the PR block carry the viewer link.
6. Comment threads, session summaries, and Markdown descriptions.

- **The web app** (D79): a neutral viewer of intxts across any number of relays, run by a relay provider, so review works from a phone's browser. MVP grade.
  - It's built in Dioxus, SSR first, as a wasm `wasi:http` component, after the `src/btress_sysadmin` precedent (Leptos SSR).
  - Given an intxt's drawer or doc id and a node that hosts it, it resolves the rest, through its own relay node.
  - Don't over-depend on that model: intxts should be viewable without a node, and webnodes are coming. So the rendering and resolving components are built to be reused by a webnode, and the relay-backed server is one host of them.
  - What "public" means is still developing; progress doesn't wait on it.
  - This is the web app, not the phone app.
- **Forge integration: deferred (D85).** The notes below stay for when it returns. It was to be designed generally (C5), with authentication and identity first, including linking a PR and an intxt (`intxt-forge-identity.md`).
  - TypeScript is usable: `src/btress_auth` runs Better Auth as a `jco componentize` wasm component.
  - No Rust port of forges.link was found (11-24); the closest is `vcs-forge`, which covers the PR lifecycle on GitHub, GitLab and Gitea and is CLI-oriented.
  - forges.link is the reference vocabulary. It is `forges`, Daniel Roe's MIT TypeScript client for 14 forges, not a protocol. Its parts that matter here:
    - refs (`RepoRef`, `ThreadRef`, `CommitRef`) with `forge` and `instance`;
    - stable keys built from the forge's own repo id;
    - `parseUrl`/`urlFor`, `parseReferences`;
    - normalised kinds and states with the raw values kept;
    - per-operation capability levels.
- **Deferred (D78):** FDR 010 and everything downstream of it waits until both goals above are done: intents, turn-id injection, fences, inline tags, the stage step, the task fence over Claude Code's newer task tools. Those are invention.
- **Plain recording of the operator's Claude Code sessions** (`record install`) is small and stays, after the two goals.
- Carried from D66: every surface is signed off by the operator using it.

## Citizenship register

Ways intxt is special-cased or ahead of the general mechanism. Each entry gives the owner of the fix and what fixes it. Keep it current: add an entry when a shortcut is taken, and close it, with its date, when it's fixed.

- **C1, `Context::call_bytes` is INTERIM** (#213, clay_mdk). Byte-answering node methods have no `Unary` wire form, so the review micro reads blobs through a side door. Fix: a byte body in `method_core` that any method can declare. Owners: nodules and claytxt.
  - claytxt (11-24): agreed.
    - The method declares its output as `method_core::ByteBody`, which is nodules' to settle, and `Context::call` delivers it as a stream.
    - The guest view's wake moves into the waker.
    - claytxt drives the Clay half once nodules settles the declaration, and deletes `call_bytes` then.
- **C2, the review micro's configuration is INTERIM.** The composition mints `doc_cap`/`blob_cap` for the micro's actor and writes a configuration entry at install. Fix: `#drawers` permbinds and the 6.2 domain handle, as for any micro. Owner: claytxt.
  - claytxt (11-24):
    - What exists: ADR 049 grants with `resolveCartridgePin`/`awaitCartridgeGrants` (#182, #184, #195), and the daytxt host mints cartridge micros from their uses and grants (claytxt layer 29).
    - What's missing: a micro reaching its granted `#drawers` through the 6.2 domain handle on `Cx`.
    - To drop `ReviewConfig`, the review micro declares its uses in its manifest (`#drawers` read for intxt kinds, and blobs) and reads the drawer and blob handles from `Cx`. The host part goes on claytxt's stack after its NSID layer; the micro side is intxt's.
- **C12, the web app can't show diffs yet.** Pierre's diff view mounts in a shadow root, so server-side rendering without a browser needs declarative shadow DOM (`<template shadowrootmode>`). Owner: claytxt (this week's web-components work). The kit itself renders under dioxus-ssr: it has no host or `clay_mdk` dependency, and serves `assets/tailwind.css` as a plain link without the `host` feature. Interactive pieces render static without hydration.
- **C13, a micro can't read blobs that arrive after install.** The review micro reads patch blobs that the intxt commits documents reference (`org.example.daybook.blob/<digest>`). On node-55, `BlobsScope` lists exact blob ids, so no capability minted at install covers them. **Already built by nodules** in #244 (`stack/node-67-blobs-drawer-read`): `BlobsScope.drawers` reads any blob in the inventory of a drawer the minter reaches at Read. It's checked at read time, and a read right after a write can briefly race the inventory's projection. Closed by restacking onto node-76; no new design is needed. Then:
  - claytxt mints `{drawers: [intxtDrawers]}` as the review micro's `blobCap` and grants `blobs.read`. Their layer 56 mints an empty `blobCap` until then, so the configuration decodes.
  - claytxt cherry-picks intxt's `read_blob` wiring (7224c1c0) onto their layer 27.
  - Status (11-24): intxt is restacked onto node-76 (#321). claytxt is rebasing onto it and adds the blob grant as a layer.
- **C14, micros had no clock.** CodeView needs `sleep`/`now` to pace frames. **Closed 11-24** by claytxt #317: `Context::sleep` and `Context::now`, whose guest sleep wakes the views. The review micro's CodeView switch (3a675d3c) uses them, and claytxt carries it above their tip.
  - Open in claytxt's lane:
    - ScrubStrip with owned labels and an optional viewport;
    - rows on a first render, for SSR and headless tests;
    - `from_patch` over bytes.
- **C15, a node can't be told to listen on TCP.** `node.json` has no listener setting; day_cli's boot hardcodes the Unix socket. The web viewer reads its node over TCP XRPC. Owner: nodules.
- **C16, no operator way to mint a dispatch capability.** Over TCP an anonymous call is refused (401), and the bearer must be a dispatch capability scoped to the methods called. `dispatch.mintCapability` isn't routed over XRPC, so `day exec` can't mint one. INTERIM: the viewer is configured with three shared capabilities (`INTXT_WEB_DOC_CAP`, `INTXT_WEB_BLOB_CAP`, `INTXT_WEB_DISPATCH_CAP`). Owner: nodules.
- **C17, the viewer's real access is public read.** An anonymous dispatch scope covering readDatums, pollDatums and blobs.read, over drawers granted Read to keyhive's Public agent, with no bearer at all. Folded into C11's sketch. Owner: nodules.
- **C18, minted capabilities don't survive a restart.** They live in memory, so every node restart invalidates the viewer's configuration. Owner: nodules.
  - **Redefined 2026-11-24 (operator, via nodules): C16–C18 close through pairing, not through public read.** There is no anonymous read path and no special case for keyhive's Public agent, since upstream keyhive and subduction are moving away from one special public identity. For the viewer, "public" means the relay hosting it has read access to the drawer, and the viewer reads with that access as an ordinary client. With ADR 043 pairing it gets its own approved identity on the relay, durable grants to those drawers and fresh handles on every connection, so nothing dies at a restart and no special mint path is needed. Until pairing lands, the operator-minted bearer stays.
  - **node-92 (nodules, 2026-11-24):** a capability in a request body is honoured only when it is bound to the actor the call's bearer is bound to. The viewer's three capabilities are all minted by the operator with no subject, so they inherit the operator's (`big_cabinet/authority/mint.rs`), and the viewer passes unchanged. nodules confirmed it from the code.
- **C3, the cartridge is published with the fixture key** (`sign_as_example`). Fix: the publisher signing namespace / DID, which the operator deferred on 11-18. Owner: nodules.
- **C4, intxt's CLI is compiled into `day`** (`src/day_cli/cmds/intxt*`). A cartridge can't contribute commands, so intxt is a special case in the node's own binary. Fix: cartridge-contributed CLI verbs, or a generic `day x <cartridge> …` dispatch over the cartridge's methods. Owner: nodules.
  - Nodules' leaning (11-24), with a written proposal to follow: `day x <cartridge> <verb>` resolves a command binding (consumer-owned metadata naming a method NSID, their D2b) and derives its flags from the method's Lexicon `parameters`/`input`, so the manifest carries only the verb name and help text. A host-side CLI component comes later, for verbs that need local files or a TTY.
  - **Rule meanwhile: every new intxt verb is a thin layer over a method,** so it ports mechanically.
- **C5, forge data is intxt's.** `day x intxt github` runs `gh` on the CLI's host and writes intxt's GitHub document. Fix: a forge vocabulary and cartridge that any cartridge reads (forges.link's ref, key and kind model), fetched on the node through egress (#198 `#net` permbind) with node secret storage for tokens. Owner: intxt designs it, nodules supply egress and secrets.
  - Spike (11-24, `spike/forge-probe` 7e06f6cc): forges 0.4.1 componentizes with jco and runs under wasmtime, with no WASI-hostile code.
    - It fetched GitHub anonymously and with a token, and Codeberg anonymously, all normalised, e.g. key `github:github.com/octocat/hello-world#pull_request/1`.
    - Costs:
      - the component is 16 MB, nearly all of it the StarlingMonkey runtime;
      - StarlingMonkey imports `wasi:sockets` and the filesystem whether or not they're used, so denying them is a host policy, not an import check;
      - env must be read inside `run()`, not at module top level (Wizer init).
    - Import only subpaths (`forges/github`, `forges/forgejo`, `forges/web`). The root entry breaks rolldown, through a dynamic-import cycle in the webhook translators.
    - `threadKey` is exported only from the root, so reimplement it (`${repoKey(repo)}#${kind}/${number}`) or ask upstream to export it from `forges/helpers`.
    - `auth.token` accepts a function, which fits a lazily read secret.
- **C6, comments and recording are intxt vocabularies** (`org.example.intxt.*`, `day x intxt record`), though the operator wants comments across daytxt and recording for end users' vibe-coded micros (D39, D71 follow-ups). Fix: generic families before beta. Owner: intxt.
- **C7, who wrote something is claimed, not attested.** The marker `writer` (#228) and a comment's `creator`/`generator` (D69) are claims, because the operator and an agent on one node are one attested actor. Fix: ADR 043 per-agent actors (and D49, the Claude Code plugin as a subsystem actor under intxt's). Owner: nodules.
- **C8, intxt's content documents are found by a `<kind>/main` marker over `PollDatums`** (D70). This is a convention local to intxt for "the documents of kind K in drawer D, per writer". Question for nodules: is it a cabinet-level pattern other cartridges should use, or a gap in drawer layout?
  - Nodules (11-24): undecided. They lean towards a cabinet-level roster role, because a marker plus `PollDatums` is a scan each cartridge reimplements. It touches automata's drawer rework, so they'll check with automata. Until then the marker is the interim pattern, which nodules will document as interim.
  - Operator (11-24), an alternative: the intxt's meta document lists its other documents by role, so there's no marker and no scan.
- **C9, general pieces live in intxt crates:**
  - anchors (`intxt_capture::anchor`: W3C quote and context, carried over hunks), which comments anywhere need;
  - the `DocReference` `via=` hint, general by the 11-17 decision.
  
  `short_ids` is already its own crate. Fix: move each when a second consumer appears, and design it as if one exists. Owner: intxt.
- **C10, forge credentials have no home on the node.** The CLI passes the operator's `gh` token per call; node secret storage doesn't exist. A webnode doing GitHub's device flow will need a stateless CORS proxy, because GitHub's OAuth endpoints don't send CORS headers (to verify). Fix: node secret storage (nodules), and the proxy as a relay-provider service. Owners: nodules, then whoever runs relays.
  - Nodules (11-24): secret storage is on their roadmap; `secrets_rs` already holds node keys. The proposed shape follows wasmCloud's secrets: a `#secret/<name>` permbind whose value the guest never reads. Egress injects it into requests to the hosts the binding names, for example as a header, so the token never passes through `day` or the guest.
  - Open for intxt: a forge client (the forges library) sets `Authorization` itself, so under injection it runs with a placeholder credential, or anonymous, and egress adds the header.
  - Operator (11-24): a secret could be a variant of local state, kept on one node and never synced. To raise with nodules.
  - For the web viewer, the CORS proxy is moot (D82): server-side loads are same-origin, and the server passes a credential through without keeping it. It returns only for a webnode with no viewer server behind it.
- **C11, "public" is undefined** (D79). The web app's own relay node reads intxts it was told about, but no drawer access level means "anyone may read". Fix: a public read level in drawer access. Owner: nodules.
  - Nodules (11-24): keyhive has a Public agent, a well-known key. A drawer grant of Read to Public means anyone with the bytes may read them: the content stays sealed, but with a key everyone knows. Nodules will sketch it against ADR 026's public root and relays.

## Decisions

- **D1 (2026-11-10, operator)** One intxt is one drawer.
- **D2 (2026-11-10, operator)** Clients write intxt datums directly through the generic datum writes; no API over the datums where avoidable. The nodule only does what clients can't (design §5).
- **D3 (2026-11-10, operator, recorded by the node lane)** Nodule methods act with the capability the caller presents, never the nodule's own grants.
- **D4 (2026-11-10, operator)** GitHub sync is on the roadmap, probably not this week.
- **D5 (design discussion)** A future VCS is separate from the intxt: an intxt composes artifacts and doesn't own their histories.
- **D6 (2026-11-10, operator)** Focus is the write loop ("replacing PRs"); pure viewing is later.
- **D7 (2026-11-10, operator)** Sessions: our own normalized datums with ACP-compatible naming (O1); one doc per session, subagents as linked sessions (O2). Later option: variant sessions as Automerge forks of their parent session doc.
- **D8 (2026-11-10, operator)** Design philosophy: datums are containers/records of history. Multiplayer editing may use other datums over the same use case, but not by default.
- **D9 (2026-11-10, operator)** Work structure (tasks, decisions) is its own datums; adapters can map harness task systems (todo lists, plans) into them.
- **D10 (2026-11-10, operator)** Agent interface: MCP, CLI and hooks all eventually; the first shipped use case sets the order.
- **D11 (2026-11-10, operator)** Evidence coverage across stacks (U10) is deferred past this week; keep it enumerated.
- **D12 (2026-11-10, operator)** FDRs: one for the general system, one per shipped feature, starting with the first. FDRs describe what users do, and users include harness adapters, GitHub, agents, humans and supporting software. No reference-model internals in FDRs.
- **D13 (2026-11-10, operator)** Multiplayer is a requirement for every datum: concurrent writers must not clobber each other.
- **D14 (2026-11-10, operator)** First feature: the agent review loop (capture → phone review → agent picks up feedback → next revision), aimed at needs today's tooling serves poorly (e.g. Claude remote control shows no files or diffs).
- **D15 (2026-11-10, operator)** The intxt graph is over arbitrary datums, not filesystem-first. A reference is a datum ref pinned at heads plus a selector into that datum; nothing more is needed in the core. Code (file docs), git/jj objects, sessions, guides and CI results are all just datums. Supersedes the multi-kind `Target` union in `intxt-design.md` §3.
- **D16 (2026-11-10, operator)** No VCS units in the intxt. intxt and a future VCS may have separate change units. "Logical change" (O5) is not a v0 concept; grouping is a structure datum with several references.
- **D17 (2026-11-10, operator)** Git/jj objects are imported as datums (commits; jj op log objects if needed). All observed commits are kept; a separate ref/bookmark datum points at a commit, and walking parents from it visits only reachable commits. No predecessor links: the ref datum's own Automerge history records what it pointed at before (a reflog for free), which gives revision-to-revision pairing.
- **D18 (2026-11-10, operator)** No verdicts in the alpha: intxt isn't managing trunks, so approve/request-changes vocabulary waits.
- **D19 (2026-11-10, operator)** Agent interface order: harness hooks + CLI first, MCP after.
- **P1 (2026-11-10, closed 2026-11-10: superseded by D29/D32, single-writer worktree docs removed and replaced per doc) (proposal, not settled; operator unsure it solves the problem; expand in ADR A3)** Unmoored work goes into a private local working set of docs; intxts are made from it afterwards. The footgun it addresses: Automerge can't unsync changes, so moving work out of an intxt is a revert, not a reset, and shared genesis history follows a doc wherever it goes. Rebuilding docs with synthetic history to shed unrelated changes is not an optimisation to tackle now. This is the main cost of the reference model.
- **P2 (2026-11-10, closed 2026-11-10: superseded by D26, then D29)** The working log as a local branch of the file doc (ADR 007 `BranchDoc`/`MergeDoc`, implemented): capture writes per-edit changes to a private, unsynced branch; promotion merges it (keeping per-edit provenance natively); broken or unwanted work is discarded by not merging, or by merging only up to chosen heads (a prefix). Constraints found: a merge carries every intermediate state (junk or secrets) with it, so the only way to drop a middle state is a squash replay; a branch needs its origin doc to exist, so work recorded before any intxt needs a root doc, and a per-repo root shared by several intxts reintroduces shared genesis (P1). Operator wants a usable default, not knobs. Also considered: the day node watching the checkout continuously like Delta's `worktree mount` (delta-claude source: hooks record only the conversation; files sync through a separate mount process).
- **D26 (2026-11-10, operator)** Git commits are the base layer; intxt does not do its own version control. File docs follow refs, not the working tree: written only when a tracked ref moves, never on checkout, staging or working-tree edits. Intermediate edits stay as patches in session docs. Live per-edit file tracking is a separate future doc kind (editor/LSP integration). An intxt may track several refs, so one path may have several file docs (one per ref). Two machines recording independently make two intxts. Supersedes P2 for code. Ingestion is deterministic in content but each writer is its own Automerge actor; no actor-id tricks to make concurrent ingestion converge (operator), P3's read-at-pins rule handles it.
- **P3 (2026-11-10, closed 2026-11-10: moot under single-writer worktree file docs, ADR 040)** Multi-writer file docs without a winner: (1) file content is always read at a commit's pinned heads, never at "current"; (2) a writer splices from the doc's actual current text to the commit's content, never from its own last write, so a concurrent splice by another machine is transient and the next write repairs it; (3) concurrent moves of one ref conflict on `gitRef.target` and both `refMove`s stay, shown as a divergent ref until the next move (jj's conflicted bookmark); (4) which doc holds a ref's path is a datum slot; if two machines create one concurrently, the loser's doc stays readable through its own commit datums, only future writes go to the winner. A new ref whose base commit is already in another ref's file doc branches from it (ADR 007) so cursors carry. Merges: file set is the paths changed between merge-base(base, tip) and tip (GitHub's three-dot "files changed"), so merging the base in adds no file docs.

- **N4 (2026-11-10) Automerge already has a sub-document URL grammar** (automerge-repo main, `AutomergeUrl.ts` and `src/subdoc-handles/{types,parser}.ts`; release not yet identified, read through a summarizing fetch, so verify against source before relying on details): `automerge:<docId>[/<path>][#<heads>]`. Heads go in the fragment, `|`-joined, each bs58check, sorted. - **N5 (2026-11-10) How datum references encode slots today, and the problems** (`big_cabinet_core/reference.rs`): a slot is bytes. `DatumKey`'s string form is `tag/` + the slot as a Go string-literal body (printable Unicode kept, `\\xNN` for invalid bytes). The URI form then percent-encodes that string but leaves `/` raw, so the slot runs to the end of the path: `db+datum:/self/org.example.note/quote%5C%22…` (double escaping: `"` → `%5C%22`). Problems I should have flagged earlier: (1) slots containing `/` make the slot unbounded, so nothing can follow it, and a selector path can't be appended without ambiguity; (2) the leading `/` makes the path hierarchical, so WHATWG parsers normalize dot segments (`new URL("db+datum:/zDoc/tag/../x").pathname` is `/zDoc/x`), which is why the code must reject `.`/`..`; without the leading slash the path is opaque and isn't normalized (tested in Node), as with `automerge:<docId>/<path>`; (3) Correction (2026-11-10): Go escaping is not redundant. It exists because Automerge map keys must be valid Unicode strings while slots are bytes; the escaped `DatumKey` string IS the Automerge key (`docs/wiki/docs.md`: slots are expected to be UTF-8, Go literal escapes for non-UTF-8 values; no recorded reason for choosing Go's format specifically, beyond a specified reversible spelling with published vectors that leaves UTF-8 untouched). The URL should therefore percent-encode the stored key string, exactly as automerge-repo encodes any map key, rather than re-encode raw bytes. Datums are stored at `ROOT/"datums"/<DatumKey string>` (`big_cabinet/doc.rs`), so a datum is literally an Automerge map path.

  - On-disk `save()` is 0.16–0.24× input for every variant (#76: one doc 1.2 MB, per-file docs 1.4 MB total, patch-as-Text 0.8 MB, plain Str 1.6 MB). Size is not the problem.

  - Build edits with line-diff splices; automerge's `update_text` is character-level and 25× slower (447 s vs 17 s) with 7× the patches.

- **F8 (2026-11-10) ListDatums cost and a write ceiling** (bench `doc::e2e::bench::list_datums_cost`, ignored, uncommitted in mothership `~/scratch/townframe-intxt`; release aarch64; N=100/300/1000 rerun by me). Notes of ~300 B, one slot each. ListDatums: 100 slots 104 ms, 300 → 0.91 s, 1,000 → 5.1 s, 5,000 → 25.5 s; current and historical heads cost the same; RSS flat (listing adds nothing to the loaded doc). Creation still succeeds. Write cost also grows with the doc (2 ms/datum at 100, 12 ms at 1,000).
