### Resumed GC decision: finite task authorization and durable domain boundary (2026-10-10)

User approved mandatory origin-authenticated finite task lifetime, applying to admission, retries, sleeping/restarted continuations and already-running attempts; managed publication/success must be fenced after expiry. A long-lived routine persists domain state and uses successor tasks with new IDs/deadlines and a stable domain idempotency identity. This forces ordinary short-lifetime tests to exercise the same checkpoint/idempotency obligations as long partitions; durable storage enables but does not itself guarantee idempotency. Reproducibly randomized successor intervals belong in domain-contract testing.

ADR 011 §10a records the full rationale and scenarios: descendants need not have seen a task, old/new partition intermediaries can reintroduce pruned work, router authority is not global settlement knowledge, and incomplete/per-epoch Bloom filters do not establish deletion. Safe expiry supplies permanent stale-execution rejection, allowing execution tombstones to be collected after the explicit clock-safety margin. Result archives, outstanding acknowledged-delivery protocols, and retired transport allocations have independent retention obligations.

Restart reliability applies to the entire domain/task interface, not only expiry: durable submission/outcome identity and domain acknowledgement, transient channels only as hints, acknowledgement releases notification retention. No promise of retaining failures forever or losing them on restart. Clock skew/rollback bounds, exact effect-fence linearization, Relay-verifiable deadline binding and the acknowledgement API still need concrete implementation design; no numerical default TTL was selected.

Resume the pre-pause task: complete garbage-triggered rotation plus safe physical reclamation/allocation fencing, now incorporating finite-lifetime admission/execution and expiry-safe collection. First audit existing optional deadlines, dispatch continuation/effect boundaries, retained outcomes and BigSync removal APIs; do not claim the new ADR policy is implemented merely by documentation. The Quint owner continues separately and models current source, not assumed future TTL enforcement.

Initial resumed source audit: `tasks/model.rs::TaskDeclaration` still uses `Option<i64>` for `not_after_secs`; its canonical digest already covers the deadline, but `validate_local` requires one only for finite ticket-authoritative result retention. `rt/triage.rs` still projects tasks with no deadline, so successor identity and lifetime must change together rather than reusing an expired deterministic task ID. `rt/task_adapter.rs` checks optional deadlines during classification/release and readiness wake selection; its outcome subscription rereads durable DispatchRepo state after channel hints, but that is not yet proof of a durable domain outcome acknowledgement protocol. These existing checks do not establish cancellation/effect fencing for running or resumed attempts. No expiry-safe physical collector may be enabled on this evidence alone.

5. **Processor predicates and execution meaning — baseline decided.** Offer snapshot and delta predicate styles according to processor design. Delta-dependent execution compares against the last successfully incorporated settlement, not the last admitted/evaluated heads. Enqueueing, cancellation, and failure do not advance processed heads. Capture the exact baseline and target in each invocation and bind the baseline into deterministic task identity when it affects input. Overlapping deltas during an in-flight attempt are accepted. An older success winning finalization settles only its own generation; existing invocations retain their capture. This decision does not add debouncing, queue coalescing, or distribution-mode migration.
6. **Unified slot state and retained processed heads — agreed direction.** Use the same processor-slot bookkeeping, settlement writes and walker sparse projection for local-only and distributed processing. Retain exact incorporated source heads with processor/config generations in settlement; this enriches evidence without reopening existing settlement semantics or preferring incremental execution. Local-only processor parts remain node-local: no remote subscription, advertisement or serving. Distributed parts synchronize only through explicit composition and native authority. Per-node processing retains independent node-local baselines despite identical logical slot identities. Replace the separate local ProcessorRunLog path in the unified cutover, preserving durable incorporation-before-settlement and accepted concurrent evidence/retention rules. DeltaWalkerSparseStateRepo is the local transactional projection, not the replicated slot store itself. Remaining work is implementing and proving these contracts, not selecting new settlement policy merely because heads were added.

## Processor/pool ownership and late-original recovery discussion (2026-10-07)

Agreed design direction, not implemented by the authority-lifecycle PR:

- Pools remain independently understood by the generic task system; processor pools are only one kind of pool.
- Node plug configuration stays in its existing shared plug-config document and references a processor-configuration document. Do not embed collaborative processor/pool configuration in node plug configuration.
- Processor configuration and generic pool configuration use separate facets in the same collaborative document. Each processor configuration contains one explicit pool reference; the task system understands the pool independently, including non-processor pools.
- Nodes can collaborate on the same processor/pool configuration without sharing node plug configuration. Processor definition/configuration, pool descriptor and authority binding are shared. Node plug configuration owns the reference and explicit local activation; capacity and available capabilities remain local runtime concerns. Local disable stops only that node's current work, not the shared processor globally. Global disable would be a separate operation.
- A retained reference distinguishes an unprovisioned processor from a referenced document that has not arrived. Reference presence must prevent ordinary missing-data discovery from silently creating a replacement.
- Disable or explicit detach stops current work; process shutdown preserves admitted durable work for recovery.

Required design-review rule: every race and hard-partition failure case must describe recovery and subsequent reconciliation when the original data finally arrives. Waiting/failing closed alone is not a complete recovery design. Record these cases as unresolved discussions, not invented implementation policy.

First concrete case: a node has the plug configuration's reference but cannot obtain the original processor/pool configuration during a prolonged partition. Recovery may explicitly create a replacement processor/pool configuration and update its local reference. Days later, the original configuration and its tasks/settlements arrive, potentially while other nodes still use the original.

Questions to resolve before implementing that recovery:

1. How is replacement creation explicitly distinguished from ordinary provisioning, and how is its relationship to the original identity/reference retained?
2. When both originals and replacements become available, do they remain distinct, require explicit selection, or support an explicit consolidation operation? No automatic winner/merge policy is agreed.
3. Which local references and active attachments change, and how are stale owners fenced without overriding another node's activation choice?
4. What happens to queued obligations, running attempts, terminal outcomes and processor settlements on both sides? Configuration reconciliation must not imply that effects were deduplicated or that one side's durable evidence may be discarded.
5. How do differing permissions, keys and unavailable source/capture data constrain reconciliation? Arrival does not itself authorize migration or execution.
6. What durable evidence makes an interrupted recovery/reconciliation resumable and prevents a later replay from silently resurrecting a retired ownership path?

Apply the same recovery-plus-late-original analysis to other race/partition cases as they are identified. Replacement creation, consolidation semantics and retirement remain open; this note does not authorize automatic recovery creation or changes to runtime behavior.
