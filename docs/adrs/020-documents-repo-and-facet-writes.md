# ADR 020: Daybook document format and DocsRepo

**Status:** Partially implemented — DocsRepo (`src/big_cabinet/doc/`) implements create, write, branch, merge, read, list, and unsafe inspection. Delete is deferred entirely (BigRepo has no document-removal primitive); the authenticated node-authority seam and history-truncating compaction remain unresolved (§1, §3, §5, §6). Cryptographic attribution consistency is implemented; historical Keyhive write authority is not yet verified by Cabinet.

## 1. Document identity and content

A Daybook doc has a `DocumentId`, a versioned content representation, and a history. Every doc is in at least one drawer and can be entered in several. Official roster inclusion, access grants, and retaining a local copy are separate operations. `DocsRepo` creates docs and reads and writes their content; `DrawerService` manages roster entries. Creation names a **placement** — a string the embedder's document-access policy interprets (for DrawerService, `drawer <id>`; §3) — persists identity and initial content before advertising authority, and then hands the document to that policy to place, idempotently, so that a crash between persistence and placement is replayed at boot. The `DrawerAccess` policy enters the doc in the named drawer and in the two local drawers for physically present and locally originated docs.

The first content representation is a map of **facets** in Automerge. A facet key has a tag and an instance name, such as `org.example.note/main`. The tag names the value's type, while the instance distinguishes facets of that type. A document can contain facets with different tags, unknown tags, and no application facets at all. Its identity and representation must remain readable without installing a plug. Other content representations may be defined later without changing document identity.

A branch is another document with its own `DocumentId` whose initial Automerge state is forked (`fork_at`) from its origin at the requested heads (`BranchDoc`), and a merge (`MergeDoc`) merges one history-sharing document's Automerge changes into another (`doc.merge`). It is not another named history *within* the source document, and it is not a value-by-value copy into an unrelated Automerge document; truncation or compaction that discards Automerge history is not a branch. A branch is committed with no groups or coparents so it stays local until placed or shared, and is placed through the access policy like a created document. Its first change writes `org.example.daybook.branch/<branch-id>` = `{ "path": "<path>", "from": { "facetRef": "db+facet:/<parent-id>/org.example.daybook.branch/<parent-id>", "refHeads": [<fork-heads>] } }` on the branch (keyed by the branch's own `DocumentId` so merging back never overwrites a target's branch identity; ADR 007). The parent reference is concrete, not `self`, so copying or merging the facet preserves its target. Unless `stealth: true`, `BranchDoc` also writes that same branch facet on the origin through the guarded, signed facet-write pipeline: non-stealth branching therefore requires `Write` access on the origin (refusing with `Denied` when the caller has only `Read` access), whereas `stealth: true` skips the origin backlink and requires only `Read` access on the origin. `MergeDoc` requires `Read` on the source and `Write` on the target, verifies through the gate that every facet touched on the source at the selected heads is accepted (`BaseNotAccepted` otherwise), verifies that the target contains the source's genesis changes (`UnrelatedHistory` otherwise), and merges the source's changes into the target. Removing a facet leaves a tombstone and history; it is not document deletion. A schema failure, missing bytes, or lost access likewise does not delete a document. Document-level deletion requires a separate core lifecycle operation and is **not implemented**: BigRepo has no document-removal primitive, so Delete is deferred entirely rather than specified against a substrate that cannot honor it. Temporary or staged adds are likewise deferred to the drawer level.

A document can recommend software through a Daybook-defined facet with a fixed, readable schema. A recommendation cannot install a plug or grant execution or write access. Program discovery and plug execution do not belong to the document envelope.

## 2. Facet values and writes

The DocsRepo API accepts a complete JSON value for each facet it sets, or an explicit request to remove that facet. It does not accept edits at JSON paths. A write may affect several facets, but unmentioned facets are unchanged. Whole-JSON reconciliation traverses the submitted value but emits only changed operations; it is not wholesale replacement of every stored object. Before committing, the repository validates new local values against the selected facet definitions, applies the declared JSON-to-storage codec, and writes the resulting content and provenance atomically. The value **read from the transaction after the content mutation** is the value committed to the facet signature. This matters when the transaction starts from already merged heads or preserves unfamiliar native values supplied in the round-trip.

Each facet Lexicon describes its canonical JSON value and is identified by its facet tag. Its sidecar JSON Schema carries the supported supplementary constraints and Automerge storage annotations. SchemaRepo supplies the known Lexicon and sidecar bundle to Cabinet; how an embedder discovers or registers bundles is outside this repository contract. A local write to an unknown facet schema is refused. Field-name suffix or prefix hints do not recover a schema and are not part of Cabinet authoring. Conflicting definitions for one tag must be reported, not silently selected by installation order. Incompatible semantic meanings use different tags; cross-version transformation is not part of an ordinary doc write.

A read-modify-write must preserve unfamiliar content in its **native storage representation**, not merely as equivalent JSON. An old reader must not turn a future collaborative Text into Str, reset a Counter, or replace an unchanged nested object's identity. Full JSON round-tripping is the chosen read/write contract. Omission means removal at the supplied base heads, including unknown properties; removing an enclosing object removes its contents. Hidden-field projection is rejected: it loses correspondence between list elements with different hidden contents and cannot naturally represent an unknown variant in a required union field. Rejecting new unknown fields and requiring a special native-copy API are not adopted. List correspondence and changed unknown-value reconciliation still need design; JSON copy/paste is expected, but cannot promise native fidelity where neither a schema, corresponding target, nor usable convention is available.

Ordinary writes must supply the heads they are based on; there is no implicit current-head write or automatic retry loop. `AtCurrent` is the explicit unsafe concurrency choice, not the default; it selects a frontier but does not bypass authenticity checks. Reconciliation must use the selected base view, not silently diff against unseen current state. Concurrent creation cannot be rejected based on an invisible remote creator: any creation-tolerance policy must also define its post-merge behavior, which remains open.

**Default reads and writes reject forged facet state at the selected heads.** A caller cannot use `write facet X at heads Y` to build on a forged X at Y, whether or not it actually called read first. DocsRepo enforces the same base-authenticity requirement before reconciliation or signing; supplying heads is not evidence that the caller verified them. Verification concerns the facet state, including hidden contributions that can affect later merges, not just the JSON winner returned to the caller. Missing or unsupported verification evidence cannot silently become a successful authenticated read or ordinary write. These checks are facet-local: a forged unrelated facet does not invalidate X. The gate implementing this is described in §6.

An older verified base remains usable through `AtHeads` even if a newer frontier contains a forgery; neither reads nor writes silently upgrade that base. Optional unsafe inspection and explicit repair are separate interfaces, not default read behavior or implicit fallbacks. A complete JSON submission alone does not select repair: ordinary reconciliation can retain native objects and hidden state from its base.

The write methods have four concurrency modes:

| Mode | Commit condition |
| --- | --- |
| `IfDocUnchanged(heads)` | Commit only if the document heads still equal `heads`; the write is based on them. |
| `IfFacetsUnchanged(facets)` | Commit only if each named facet still has exactly the facet version given (compared by heads) (empty: never written, or written by nobody verifiable), even if other facets changed; the write is based on current heads at commit time. |
| `AtHeads(heads)` | Intentionally write from existing historical document heads, producing a concurrent change if newer heads exist. |
| `AtCurrent` | Write from the heads current when the write is prepared. |

Comparison and commit are serialized for the document: the condition is checked when the write is staged and rechecked under the same document lock as the commit. A facet version is its facet heads, which cover all visible conflicting claims, deletion, and recreation—not only the displayed JSON value. Because the comparison uses *verified* facet heads, a facet that does not verify cannot match a condition taken from an earlier read. Reads return the facet heads needed for `IfFacetsUnchanged`, and can read a facet at specified document heads. Unknown heads fail with `UnknownHeads`. Supplied historical heads are never silently replaced by current heads. An error from a local write commits neither facet content nor dmeta. A successful receipt means local persistence and reports the resulting heads; it does not assert peer delivery or a particular future conflict winner.

### Wire surface, facet versions, and read states

The implemented surface is eight operations: `CreateDoc`, `WriteFacets`, `BranchDoc`, `MergeDoc`, `ReadFacets`, `ListFacets`, and the unsafe pair `UnsafeInspectFacet` and `InspectFacetClaims`. Provenance stays inside the repository: what leaves it is a **`FacetVersion`** — the facet heads (the change hashes that introduced each signature currently covering the facet; one per signature, so a concurrently written facet has several) plus a Lamport `clock` — never raw signatures. The clock is the greatest Automerge `max_op` among the facet heads: Automerge assigns every new change a `start_op` above the document's current maximum, so a version produced by writing on top of another always has a strictly greater clock, while concurrent versions are incomparable (equal clock with different heads means the versions merged or diverged, and the consumer must re-read). Facet heads are ordinary change hashes, so a caller can seek a facet's history with them exactly the way it seeks a document's history with document heads, and hand the version back to `IfFacetsUnchanged` (which compares heads exactly; the clock is an ordering hint for consumers, not part of the condition). `ListFacets` reports the slots present at some heads and their versions without returning values or verifying anything.

A read names `At::Current` or `At::Heads`. Each requested facet comes back as one of:

| State | Meaning |
| --- | --- |
| `Accepted` | Every signature covering the facet verifies and the stored value is exactly what they signed (merged by Automerge's rules where they are concurrent); carries the value and its `FacetVersion`. |
| `Absent` | Removed by a verified removal claim, or never written (version heads empty in that case). |
| `Pending` | The facet was found, but verification could not determine whether it is forged; currently an unsupported representation or verification resource limit can prevent that determination. This does **not** mean fields of an applied Automerge change are waiting to sync. **No value is returned unless the read was explicitly `optimistic`;** an optimistic value can never be written on top of. |
| `Rejected` | Proven invalid: a bad signature, or a change to the facet that no valid signature covers. The value is never returned. |
| `Undecodable` | Authentic, but the stored value cannot be read as its declaration states (or, with no declaration, has no raw JSON spelling). It can still be overwritten. |

`facet_set` is an ungated routing projection driven only by `AutomergeFrontierRevisionStore`, not by DocsRepo writes or read results. It keys routes by `(DocId, FacetKey)` and namespaces its keyed-frontier stream by facet tag. Live rows carry document heads, unverified signature-introduction heads, and their Lamport clock; removals retain tombstone heads and clock. Consumers read values through the DocsRepo gate at the reported document heads; consumers that act without reading values must provide their own gating.

`FacetSetStore::run` uses `ConcurrentDeltaWalker` and bounded keyed tasks: a newer transition supersedes work for the same document, while independent documents proceed concurrently. Unavailable documents park individually and local lifecycle notifications serve only as wakeups, never as projection input. The route effects and sparse per-document heads/epoch/cursor commit in one SQLite transaction before the walker acknowledges the cursor. A crash before acknowledgement replays idempotently. The embedder owns the run future and its cancellation and must stop it before BigRepo.

Initial snapshots, envelope replacements and materialization-epoch changes scan raw facet and metadata maps, without typed dmeta or value hydration. Incremental projection inspects only changes added between the settled and requested heads and resolves their object-parent paths. Visible `diff_obj` patches alone cannot identify hidden conflict operations, so the raw operation footprint is necessary to retain unsigned and hidden content touches even when presence and signature heads are unchanged. Shared provenance changes conservatively invalidate affected routing state. Current-head reads use non-historical Automerge methods; a live handle ahead of the source revision is read at the exact source heads instead. Keyed-frontier replay is latest-state catch-up, not an append-only audit log.

### Two-phase write and the command ledger

A write runs in two phases so that nothing is signed that cannot be committed. The write is first staged in a transaction with placeholder signatures and rolled back, so every refusal — schema validation, dmeta reconciliation, the base-authenticity gate — surfaces before anything is signed. The claims derived from staging are then signed, the identical transaction is restaged with the real signatures, and the condition is rechecked under the same document lock as the commit. Every change DocsRepo makes on a document uses a per-document Automerge actor: the 32-byte node key followed by the first 16 bytes of `BLAKE3(document_id)`. Appending the document tag prevents `(actor, seq)` collisions when a branch and its origin are both written on the same node and later merged; a write at historical heads uses Automerge's derived concurrency actor, which still ends in those 48 base bytes. The gate recovers the claimed 32-byte node key from that identifier, though the identifier alone does not authenticate the change's node signer (§3).

Creates, branches, writes, and merges accept a caller-chosen `CommandId` (1–256 bytes; required on creates and branches, optional on writes and merges) as an idempotency key. The `big_cabinet_commands` SQLite table replaces the old outbox: a row is inserted **before** the command's first durable side effect (`kind IN ('create', 'write', 'branch', 'merge')`, with `detail_json` carrying branch origin/path/stealth or merge source heads) and advanced pending → committed → done, with `done` written only once everything the receipt asserts is durable. Each row stores a digest of its request, so a completed command replays its stored receipt, an in-flight one is refused (`CommandInFlight`), and an id reused for a different request is refused (`CommandReused`). A completed row answers replays for 7 days; a retry after that re-executes. Boot recovery settles what a crash left behind using facts that already live elsewhere: a create's or branch's BigRepo reservation and Keyhive document say which side of `commit_id` the crash fell on (and for a committed non-stealth branch, whether the origin already carries a backlink change whose commit message is the command id before placing the branch); a write's Automerge change carries its command id as its commit message, so whether it was committed is read off the document itself; and a merge adds no change of its own, so its pending row is settled as `done` if the target holds all of the recorded source heads and discarded otherwise.

Write, branch, and merge refusals are `Denied`, `Access`, `InvalidCommand`, `CommandInFlight`, `CommandReused`, `UnknownSchema`, `SystemFacet` (`dmeta` cannot be written or read directly; `org.example.daybook.branch/*` is readable but can only be written by `BranchDoc`), `SetAndRemoved`, `InvalidValue`, `Conflict`, `BaseNotAccepted` (a touched facet's base verdict — or, for `MergeDoc`, any facet touched on the source at the merged heads — was `Pending` or `Rejected`), and `UnrelatedHistory` (`MergeDoc` between documents that do not share genesis changes).

Automerge is the initial concurrency substrate, **not the definition of a signed facet**. At historical heads, a write can create another concurrent version; that is not a new document branch. A later merge may display a value different from either writer's transaction view. Such a computed view must not be attributed to either signature as though that actor signed the later result. A subsequent writer can sign that merged view as a new claim through the ordinary path only after the repository verifies its base; seeing the materialized value through an unsafe read does not satisfy that requirement.

## 3. Node authorization and local capabilities

The required trust anchor is the **authenticated node signer**, not the forwarding peer and not an Automerge actor identifier supplied by the change. Cabinet currently recovers a claimed node key from the Automerge actor and verifies that the actor-attribution certificate is signed by that key. This establishes cryptographic consistency, **not** that the node was permitted to write the document. Binding this key to the authenticated substrate signer and querying historical Keyhive Write authority are deferred until the Keyhive integration/migration is settled. No historical-membership algorithm or Keyline content-revocation policy is selected here. Unknown external node authority is a legitimate reason for verification to remain unresolved once that seam exists; missing in-document bindings or certificates are not.

The host also checks local plug/actor policy before allowing a local write and validates that write's facets. A hostile node with document Write authority can bypass its own plug checks; a receiver cannot infer that a remote plug or validator ran. An alternative in-document authority graph was considered and rejected: granting access should not require editing every affected document. Authority grants remain outside document content.

Local capabilities and portable attribution are separate contracts. An actor's signing identity is its public key; names and paths confer no authority. Issuing or revoking local actor access does **not** mutate documents or invalidate historical attribution. A branch has a different document ID and does not inherit drawer entries merely because it records an origin. The same authorization boundary applies across local IPC: a transport is not proof that a caller controls an asserted actor.

ADR 022 now specifies one scoped domain cap per resource request, with authority and signer proved separately at mint time. The cap's bound signer supplies attribution, not additional access; identity proofs have no fallback path on a resource call. A domain cap must not expose an actor proof or allow arbitrary direct signing outside its scope. Namespace minting authority is provisioned separately from actor identity.

Access policy remains owned above DocsRepo through `DocAccess`, answering `Read`, `Write`, and `Create { placement }`, where `placement` is the policy's own spelling. `DocAccess::prove` validates the whole requested scope at mint time and returns revocable support dependencies from the owning domain's grants; scoped membership queries remain necessary on use. The standalone `LedgerAccess` policy stores document and placement grants locally through `Grants` when drawers are not configured; it does not call central Authority grant RPCs. The policy also *places* each created document after identity and initial content are durable and before creation is acknowledged. The boot pass replays placement after a crash, so placement must be idempotent and use stable operation/actor data rather than expired capabilities. Creating an actor or handing it a dispatch cap does not implicitly give it standing document grants.

Unsafe inspection is kept — it is useful for tests and diagnostics — behind a separately minted per-document capability in the `DocsRepo/UNSAFE/inspection/v2/` domain encoding, with its signer bound at mint time. It is never a fallback of the ordinary path and never makes the inspected heads eligible for an ordinary write.

The design direction is the authority service (ADR 022) owning runtime routine capabilities, including document, facet, command, and SQLite handles exposed through WIT. That is **not a PR3 runtime migration** or a selected portable capability-token format. Dmeta's `delegation` field does not carry those live capabilities. Private-key custody is likewise a host boundary, with secrets kept in `secrets_rs` and signing exposed without handing keys to callers; the cryptographic protocol does not depend on that particular custody implementation.

Dmeta records **who claims authorship of a facet**, not the host's current capability policy. A node may attribute an actor to an application or process, but its certificate proves the node made that attribution, not that a particular binary executed. Node change signatures, actor-attribution certificates, actor facet signatures, and local capabilities are distinct artifacts.

## 4. Signed facet claims

A facet key selects a slot in the document. Dmeta retains every UUIDv7 alias assigned to that slot by concurrent creators; external references to any alias remain valid. For a new signature the chosen UUID is the lexicographically smallest alias **visible in the writing transaction**. History reconstruction recovers that same choice at the change introducing the signature; portable evidence carries it in the signed message. A later merge may add a smaller alias without changing what was signed. The facet's content is the materialized value at its key, not a value selected by UUID.

The aliases also retain evidence of **concurrent creation** after later writes hide the original Automerge conflict. Convergent facet keys let two OCR processors target the same slot; distinct creation UUIDs let an index distinguish those independent creations durably. They do not select a different content winner. UUID timestamps are metadata, not trusted chronology, even when a signature authenticates the UUID bytes.

A facet signature authenticates a **substrate-independent logical claim**. Its seven fields are the origin document ID, facet key, chosen facet UUIDv7, actor UUIDv7, Set or Remove operation, CID of the transaction-view native value for Set (null for Remove), and sorted predecessor signature IDs. Predecessors record the signatures visible at the selected base heads. They are signed context, **not a recursive trust gate**: a rejected predecessor does not poison a fresh, valid replacement. A new facet has no predecessors; resurrection can name the visible tombstone. Signing identical content with the same key, actor binding, and claim context produces the same signature. Writing at historical heads uses that context and may produce a concurrent signature.

In ordinary Automerge storage, the repository reconstructs the message from the change that introduced an immutable signature entry rather than storing a duplicate claim object. This is a storage optimization, not a dependency of the protocol on Automerge. `FacetSignature.message` can carry the **complete domain-prefixed signed message**, including chosen UUID and predecessors, for history-free export or compaction. Carrying only the current value CID would not preserve the claim context.

The value CID is CIDv1 with `raw` codec and **BLAKE3-256** multihash (code `0x1e`) over the canonical native bytes. The native form is what the signature covers because the JSON spelling of a stored value depends on its declaration: a float leaves as a decimal string, a counter as a whole number, a timestamp as RFC 3339, bytes as `{ "$bytes": "…" }`. Native `Bytes`, `Counter`, and `Text` remain distinct from other kinds, so verification of a native value needs no facet schema. An absent schema leaves it uninterpreted rather than cryptographically invalid. Portable JSON can preserve verification when a schema or typed witness faithfully reconstructs the native kinds; untyped flattening can lose that information.

The canonical encoding is CBOR of the materialized subtree, one application-private tag per storage kind, **unique map keys sorted by their encoded bytes**, and no object, actor, or operation IDs. Copying a value changes its object identity, not its value CID. `Text` encodes its current plain string and `Counter` its current sum, each still distinct from `Str` and `Int`. The tag number is the private base `0x64626b00` plus a kind index, not an IANA registration: 0 null, 1 bool, 2 int, 3 uint, 4 float, 5 str, 6 bytes, 7 timestamp, 8 counter, 9 text, 10 list, 11 map. Timestamps encode milliseconds since the Unix epoch. Containers have definite lengths and other payloads use the shortest RFC 8949 representation, except that **every float uses binary64**: all NaNs normalize to positive quiet NaN bits `0x7ff8000000000000`, infinities are preserved, and positive and negative zero remain distinct. Changing kind indices or canonicalization rules requires a new protocol version. `encode_native` implements this encoding; a claim holds only the resulting CID.

Only plain Automerge text is covered. Marks, embedded blocks, tables, and unknown scalar representations are unsupported until their encoding is specified. An unsupported representation or traversal resource limit is not evidence of forgery. The value encoding covers a visible materialized value, **not hidden Automerge conflicts or a proof of all operations that produced it**.

V2 signs `UTF8("daybook.facet-claim.v2") || 0x00 || CBOR(fields)` with Ed25519 and strict signature verification. `CBOR(fields)` is a deterministic definite-length array in this order:

1. Origin document ID as canonical UTF-8 text.
2. Facet key as UTF-8 text.
3. Chosen facet UUIDv7 as a 16-byte string.
4. Actor UUIDv7 as a 16-byte string.
5. Operation: `0` Set or `1` Remove.
6. Value CID as binary bytes, or null for Remove.
7. Predecessor IDs as an array of binary CIDs, sorted lexicographically without duplicates.

The signature covers the whole message, not merely the value CID. Its ID is a CIDv1 `raw`/BLAKE3-256 multihash of `UTF8("daybook.facet-claim-id.v2") || 0x00 || actor-public-key-bytes || signature-bytes`. Both domains are v2 because the signed field layout changed. The ID does not hash `signed-message-bytes` directly (which is omitted in Automerge storage and contains `predecessors`, so hashing it would make computing a parent signature's ID recursively reconstruct the entire ancestor chain back to genesis; Ed25519 `signature-bytes` already commits to `signed-message-bytes`) and does not refer to its containing Automerge change hash, which would be circular. Actor public keys use canonical base58btc multibase `z…` text in metadata; signatures are native 64-byte `SignatureBytes`, rendered in JSON as `{ "$bytes": "<base64>" }`. Messages and retained native-value witnesses also use the bytes object, not multibase text.

## 5. Actors, attribution, and dmeta

An actor's cryptographic identity is its public key. `actors` assigns a UUIDv7 to a binding of that key and an exact actor URL. The same key may have several UUID bindings, each with its own attribution certificate. The URL is descriptive metadata, not an authority namespace; the certificate authenticates the description without proving a plug binary executed. The Automerge change actor remains the node, while the actor key signs the facet claim.

### Attribution certificate profile

Despite its field name, `ActorMetadata.delegation` holds a **neutral node-signed attribution certificate**, not a grant or redelegation chain. It binds the issuer, actor UUIDv7, actor public key, and exact actor URL. Verification takes an **externally authenticated expected issuer** from the caller and compares it with the certificate's issuer; accepting the certificate's self-declared `iss` as the trust anchor would let anyone mint a replacement identity. The certificate does not make the actor a Keyhive principal, confer transitive issuer trust, or require a live authority-service query.

The profile uses CWT claims inside tagged COSE_Sign1:

```text
61(18([bstr(protected), {}, bstr(claims), bstr(signature)]))
protected = {
  1: -19,
  2: [16],
  3: "application/cbor",
  16: "application/vnd.daybook.actor-attribution.v1+cwt"
}
claims = {
  1: issuer,
  2: actorPublicKey,
  -65537: actorUuidBytes,
  -65538: actorUrl,
  -65539: "daybook.actor-attribution"
}
```

`issuer` and `actorPublicKey` are canonical base58btc multibase text of raw 32-byte Ed25519 public keys, not multicodec-prefixed keys. `actorUuidBytes` is the raw 16-byte RFC-variant UUIDv7; `actorUrl` is exact text with no normalization. The media type above is **private and unregistered**. Protected header 16 is critical, and the protected algorithm is fully specified `Ed25519 (-19)`, not deprecated polymorphic `EdDSA (-8)`. The signature is pure Ed25519 over the CBOR Sig_structure `["Signature1", bstr(protected), h'', bstr(claims)]`, with empty external AAD.

This is a closed profile: no `iat`, audience, expiration, grants, or redelegation fields. The unprotected header map is empty. Unknown extensions, other algorithms or profiles, duplicate map labels, trailing data, malformed bindings, weak or noncanonical keys, and invalid signatures are not accepted. Verification uses the **received protected and payload bytes**, not their re-encoded equivalents. Resource bounds are 4096 certificate bytes, 2048 actor-URL UTF-8 bytes, CBOR depth 4, 64 items, and 16 entries per collection. Unsupported profiles and resource-limit refusals remain distinct from malformed or cryptographically invalid evidence.

The standards define the envelope and signature processing, not Daybook authority: [RFC 8392 §§3–7 and §9.1.1](https://www.rfc-editor.org/rfc/rfc8392.html) defines CWT and private claims; [RFC 9052 §§3.1 and 4.2–4.4](https://www.rfc-editor.org/rfc/rfc9052.html) defines COSE headers and Sign1; [RFC 9596 §§2–3](https://www.rfc-editor.org/rfc/rfc9596.html) defines protected `typ`; [RFC 9864 §2.2](https://www.rfc-editor.org/rfc/rfc9864.html) defines the fully specified Ed25519 algorithm. A capability-delegation format would assert different semantics from this attribution-only certificate.

### Dmeta storage

`org.example.daybook.dmeta/main` is the Daybook-owned provenance facet. Its logical structure is:

```text
Dmeta {
  createdAt: Timestamp
  updatedAt: [Timestamp]
  actors: Uuid7 -> { pubkey, actorUrl, delegation?: Bytes }
  branchUuids: Uuid7 -> DocumentId
  facetUuids: Uuid7 -> FacetKey
  facets: FacetKey -> {
    updatedAt: [Timestamp]
    deletedAt: [Timestamp]
    signatures: [ {
      actorUuid: Uuid7
      docUuid: Uuid7
      signature: SignatureBytes
      message?: Bytes
      inherited?: { originDoc, message: Bytes, value?: Bytes }
    } ]
  }
}
```

The enclosing document's own ID is not a single top-level field of `Dmeta`: a single field inside the facet would be copied onto a branch and overwritten on merge. Instead, `branchUuids` maps each document UUIDv7 alias to the `DocumentId` where signatures carrying that `docUuid` were introduced, while branch relationships are weak links recorded by `org.example.daybook.branch/<id>` with a concrete parent facet reference and fork heads (ADR 007).

`facetUuids` is the only facet-alias index: each UUIDv7 maps directly to a complete facet key, tag and instance together. `branchUuids` is the corresponding document-alias index for history-sharing documents: when a document writes, it reuses the lexicographically smallest `Uuid7` already bound to its `DocumentId` in `branchUuids`, or binds a freshly minted `Uuid7` on the first write on that document (for a branch, the initial write of `org.example.daybook.branch/<branch-id>`). Like `actors` and `facetUuids`, bindings in `branchUuids` are immutable once written. Actor, document, and facet UUID times replace separate per-binding creation-time fields, but do not establish a trusted order of events.

For an ordinary Automerge write, a signature entry carries `actorUuid`, `docUuid`, and native signature bytes; the remaining claim context — including `origin_document`, looked up from `branchUuids[docUuid]` at the introducing change — is reconstructed at its introduction change. Because a branch (`fork_at`) or merge (`merge`) carries the introducing Automerge changes themselves across documents, an ordinary signature entry reconstructs to the exact `origin_document` it was signed on whether it is read on the origin, on a branch, or after merging back, without needing an `inherited` witness. Actor keys and certificates are shared through `actors`. The optional `message` preserves a locally authored claim when that reconstruction will no longer be possible. `message` and `inherited` are alternative evidence carriers, not fields to populate together. Automerge applies a change only with its dependencies; a readable signature entry cannot be waiting for its introducing change or for other operations from that same change. A missing alias, unbound or conflicting `docUuid`, actor binding, required signature field, or attribution certificate at the entry's introduction is malformed evidence, never a sync-pending state. Omitting `message` is valid while the claim is reconstructible from retained history; a history-free export must carry its complete message. Unknown requested heads are a request error (`UnknownHeads`), not a facet verdict. A missing externally authenticated issuer proof is separate from these in-document structural failures.

`signatures`, document and facet `updatedAt`, and facet `deletedAt` are **current competing sets**, not append-only logs. Replacing a set removes only the entries observed at the supplied base heads; concurrent entries survive. Retained signature entries remain immutable, and newly inserted signatures get fresh objects rather than mutating old entries in place. Generic positional list reconciliation must not mix fields from concurrent signatures. Full-JSON reconciliation still traverses the value; preserving unchanged native objects and emitting only changed operations does not mean traversal is free.

`deletedAt` is always present and initialized, empty for an authored non-tombstone. A removal records a deletion candidate; a later Set clears the candidates it observed. A concurrent Remove/Set merge can retain deletion candidates even when a value is visible. Timestamps are unsigned display metadata: neither a nonempty `deletedAt` nor the latest timestamp decides current tombstone status. The signed operation and its match to the current slot state do. Older entries may remain in Automerge history without being duplicated in current dmeta. Granting broader local access creates no entries in untouched documents.

### Branches, merges, and compaction witnesses

Because a normal branch is forked from its origin's Automerge history and a merge combines history-sharing Automerge documents, signatures travel with their introducing changes and reconstruct through `docUuid` and `branchUuids` without `inherited` witnesses. By contrast, a history-truncating compaction or history-free import discards the Automerge changes a signature's claim would be reconstructed from; a signature retained across compaction therefore carries an `inherited` witness: origin document, the exact domain-prefixed signed message, and, when the compacted value differs from the signed one, the canonical native bytes of the historical signed value. Keep these witnesses even when they do not cover the current value. They authenticate only their own claim; an authentic historical value is not a signature on a differing merged value. A signature authored on a branch or after compaction names its own document through `docUuid` and uses its own reconstructible history or optional `message`, not `inherited`.

A carried message allows cryptographic verification without the source's Automerge history. It does not by itself prove node admission on the origin or establish the expected attribution issuer. If required authority evidence is missing, that check remains pending rather than forged. Export or compaction must preserve the complete messages and native-value evidence needed for the claims it retains; **omitting carried evidence is an Automerge-history-specific optimization**. Neither copying values nor preserving messages recreates discarded operations or hidden conflicts.

For example, node N certifies actor binding A, whose key signs facets X and Y in D. On a normal branch B forked from D, X and Y keep their ordinary signature entries whose `docUuid` resolves to D in `branchUuids`; when A replaces X on B, B's first write has bound a `docUuid` to B, so the new claim names B as `origin_document` and names D's signature ID on X as predecessor context, and merging B back into D preserves both B's signature on X and D's signature on Y. Under a history-truncating compaction, the retained signatures carry `inherited` witnesses naming D instead; reconstructing or accepting a derived merge after compaction remains unresolved (§6).

## 6. Verification and presentation

Authenticity is **facet-local**, not whole-document validity or recursive predecessor closure. For an ordinary Automerge signature, reconstruct the claim at the change that introduced its immutable entry: read the transaction-view native value or tombstone, key, chosen alias and actor binding there, and predecessor IDs from its parent heads. Do not substitute today's value or alias choice. For a portable or inherited entry, decode the carried complete message; when reconstruction is also available, the messages must agree. Check actor UUID, key, alias, facet key, and origin context, then strictly verify the signature and the attribution certificate against the caller's authenticated expected issuer. An inherited retained value must match its signed CID, but it is not evidence that a differing current value was signed.

BigRepo and Keyhive separately gate node admission below Cabinet. A write performed now uses current local capabilities even if its explicit base heads are old. Portable witnesses do not remove the caller's obligation to supply any required origin-authority evidence.

The read/write gate required by §2 is implemented. Every change that modifies a facet's content also introduces a signature on that facet, and the signature covers the facet's value as that change left it; the facet's **facet heads** are the introductions of the signatures currently covering it. Facet X at heads H is accepted when three conditions hold:

1. **The current signatures verify.** Each claim, reconstructed at the change that introduced its immutable entry, matches the signed bytes, and the actor's attribution certificate verifies against that change's claimed node key. The limitation of this issuer anchor is explicit in §3. A proven-invalid current entry rejects that facet, never an unrelated facet. An inherited claim must also cover the native value or removal at its import change; counting the import itself as a facet head cannot turn a historical signature into a signature on different content.
2. **Nothing touched X outside them.** Every change in H's ancestry that touched X's content or signature containers and is not already beneath the facet heads must itself introduce a valid signature on X. Replacing or deleting the shared content or provenance envelopes also touches every previously recorded slot: erasing a signed removal cannot turn it into a never-written slot. A change that touched X without signing it — even one whose value lost an Automerge conflict and is not visible at H — is a forgery and rejects the facet.
3. **The value is what they signed.** The native value at H equals the native value at the facet heads — the signed values merged by Automerge's own rules. This stops signature entries from being deleted out from under a value.

Changes beneath the facet heads are not re-examined: whoever signed on top of them passed this same gate for their base first. That is why a hidden unsigned contribution cannot be laundered — an honest writer's base check sees it (it is not beneath the signatures that existed then) and refuses to sign — and what keeps a slot recoverable: an explicit repair signs a new value and the old forgery falls beneath it. Verification that cannot complete because a representation is unsupported or a resource budget is exhausted leaves the facet Pending, not proven forged. Missing required document metadata is Rejected; it cannot arrive later at the same historical heads. Internally observed operation IDs must resolve to applied introducing changes; failure of that invariant is a repository defect, not a pending facet. Checks are facet-local: a forgery in another facet changes nothing. The write path runs this gate on the write's base before reconciliation or signing and records the covered signatures' ids as the new claims' predecessors.

The current per-entry value-verification states distinguish authenticity from value coverage:

| State | Meaning |
| --- | --- |
| `Accepted` | Claim and attribution verify, and the signed Set value CID or Remove operation matches the supplied materialized value or removal; this is not full frontier validation. |
| `Pending` | A snapshot-only helper was not supplied reconstructed message/value evidence or an external expected issuer, or verification cannot complete for an unsupported representation or resource limit. This helper has no Automerge document to reconstruct omitted messages from; it does not imply partial visibility of applied changes. |
| `Rejected` | Claim/signature/context or attribution evidence is invalid. A proven invalid check is not repaired by missing evidence elsewhere. |
| `Uncovered` | An authentic claim does not match the current value or removal; its historical authorship remains valid. A slot with no signatures is also uncovered. |

At this value-evidence layer, a slot is `Accepted` if **any** signature accepts its current value or removal, even if other entries are pending or rejected. Without a matching accepted entry, the fold prefers `Pending` if any entry is pending, then `Rejected` if any is rejected, otherwise `Uncovered`. This does not relabel a rejected entry as authentic, nor prove that hidden state is safe to reuse. This permissive helper fold does not govern repository reads: a proven-invalid current entry rejects its own facet at the stronger gate. A fresh valid replacement can recover the slot without recursive acceptance of predecessor claims; their IDs record context, not a requirement to trust rejected ancestry. These per-entry states are evidence inspection, not the read surface: the gate above is the stronger check, and what `ReadFacets` returns is the §2 fold of its verdict — `Accepted`, `Absent`, `Pending`, `Rejected`, or `Undecodable`.

There is no whole-document shutdown for a bad facet signature. Rejected physical history can remain as evidence without becoming application content. Ordinary reads reject forged facet state, not merely return its displayed winner with a warning. Unsafe inspection stays separate from this path and never makes the inspected heads eligible for an ordinary write; it is implemented as the capability-gated `UnsafeInspectFacet` and `InspectFacetClaims` operations (§2, §3). Explicit repair can establish a new signed value without endorsing rejected ancestry, but must not silently retain the rejected content or hidden contributions as live state; its API remains future work, though the gate already makes a repaired slot acceptable by letting the old forgery fall beneath the new signature. Local authoring errors remain atomic; received evidence is reported through verification state.

Cryptographic checks on immutable claims can be cached. Current-value coverage must be reevaluated when the slot changes, and missing-evidence verdicts must be reconsidered when evidence arrives; a once-per-entry cache is not sufficient for all verdicts. An LRU cache for these checks is deferred. Missing schemas leave native values uninterpreted. Unsupported native representations and resource limits must remain distinguishable from a bad signature.

### Guarded reads and derived-merge edge cases

The default-path guarantee is settled: an honest actor cannot read or ordinarily write a forged facet at its supplied base heads. The following hidden-conflict scenario illustrates why a materialized-value check alone cannot implement that guarantee; it is **not a counterexample to the guarded contract**:

1. A verified branch holds `x = "safe"`. An unsigned concurrent assignment of `x = "evil"` loses the visible conflict but remains in the facet's CRDT state.
2. Through raw Automerge access or an unsafe read, A sees `"safe"`, changes another field, and signs the resulting visible value while retaining the hidden assignment.
3. B, writing from an older verified frontier that never contained `"evil"`, deletes the observed `"safe"` assignment. Merging the branches can expose `"evil"`.
4. Replaying A's and B's forks can reproduce that result, but checking their signed visible values alone missed A's forged base. **The default path must stop A at its read or base check, before A's ordinary write and signature.** B's older verified base remains legitimate.

The implemented gate resolves this without reconstructing forks: condition 2 rejects A's base because the hidden assignment is a change that touched X without signing it and is not beneath the facet heads, and condition 3 compares the real CRDT state at H with the real state at the facet heads rather than signed snapshot values. Two legitimate concurrent edits can yield a derived value neither actor directly signed; that alone is not forgery — it passes condition 3 because the value at H *is* the signed values merged by Automerge's rules. Verification thereby establishes the derivation without attributing the merged value to either actor as a direct signature. Requiring a new signature merely because a legitimate merge occurred is not selected. A write replaces the signature set it observed at its base, so after a concurrent merge the facet heads are the surviving concurrent introductions minus those the later writer observed and retired — not every introduction that ever covered the slot. A caller's `IfFacetsUnchanged` condition therefore names a precise merged version even though the merged value may be one of several its signatures covered.

Value claims also do not identify a unique CRDT operation history. Incrementing an existing counter from zero to one and replacing it with a fresh `Counter(1)` have the same native value CID but can merge differently with a concurrent increment. The gate satisfies this by construction: it reads the document's actual state at the facet heads and never substitutes an operation history reconstructed from value CIDs.

The evidence a history-free or compacted branch must retain remains open. Messages and inherited native-value witnesses preserve their signed claims but cannot recreate discarded operations or hidden conflicts. Explicit repair remains distinct from an ordinary write on a verified base. No operation-receipt format, read-receipt format, or new node-attester trust policy is selected by these edge cases.

## 7. Conformance work and measurement

Conformance and performance are separate work. Before treating the wire format as stable, publish cross-implementation byte vectors for native encoding, value CIDs, v2 claim messages and signature IDs, the v1 attribution CWT/COSE profile, and strict Ed25519 signatures. Verify canonical textual IDs and keys, native-kind distinctions, binary64 NaNs/infinities/signed zeros, encoded-key ordering, received-byte COSE verification, issuer isolation, duplicate/trailing-data rejection, and resource bounds.

Repository conformance must cover transaction-view values; writes at old heads; concurrent creators and UUIDv7 aliases; immutable competing signature entries; initialized timestamp sets; concurrent Set/Remove and resurrection; inherited and newly authored branch claims; full-message export and compaction; faithfully typed JSON reconstruction; unknown schemas and unsupported native kinds; pending and invalid evidence; uncovered current values; and recovery by a fresh valid replacement without recursive predecessor acceptance. Inspect the signed Automerge change-label payload and its handoff through Subduction separately from the facet claim protocol.

The following are DocsRepo behaviors; with the gate implemented (§6) the guarded-base rows describe enforced behavior, while the copy/compaction row remains open:

| Scenario | Required behavior |
| --- | --- |
| Forged facet X at supplied heads Y, including a hidden unsigned contribution behind an authentic-looking winner | Default read fails; ordinary write fails before content or dmeta mutation, even without a preceding read call. |
| Unsafe inspection of the same forged base | Inspection does not authorize an ordinary write at those heads; any repair is explicit. |
| An older verified base while newer heads contain a forgery | `AtHeads` uses and verifies the requested base, never silently upgrades it; later merged state is checked separately. |
| A forgery in an unrelated facet | Reading or writing authentic X remains possible; no document-wide validity fold. |
|Missing alias, `docUuid` binding, actor binding, signature field, or attribution certificate at a signature's introduction | Malformed/Rejected, not Pending; applied Automerge changes are atomic. |
| Unsigned erasure of content/provenance envelopes or signature containers, including after a signed removal | Reject the affected recorded slots, never reinterpret lost provenance as never-written; older verified heads remain readable. |
| Unknown requested heads | Return `UnknownHeads`; this is not a facet verification state. |
| Unsupported verification representation or exhausted resource budget | Verification cannot complete; never accept by fallback or call a resource refusal proof of forgery. |
| Legitimate concurrent disjoint edits | Verify the derived merge without pretending either input signature directly covers its different value. |
| Branch and merge across history-sharing documents | Fork Automerge history, record `org.example.daybook.branch/<id>` with concrete parent reference and fork heads (on the origin too when non-stealth with origin Write access), reconstruct each signature's `origin_document` via `branchUuids[docUuid]`, and refuse merges from unaccepted source facets (`BaseNotAccepted`) or unrelated documents (`UnrelatedHistory`). |
| Hidden-conflict resurrection described in §6 | A is stopped by the guarded base check; a raw-Automerge reproduction is not a successful default-path workflow. |
| Equal signed counter values produced by increment versus replacement | Do not treat equal CIDs as interchangeable CRDT histories when reconstructing a merge. |
| Explicit replacement of forged content | New authentic content can recover the slot without trusting rejected predecessors or retaining their hidden live state. |
| Copy or compaction without source history | Preserve verifiable claims and report missing derivation evidence; do not invent a merge from value witnesses alone. |

Native, attribution, and claim conformance tests exist in the source. Wire snapshots pin serialized DTOs; table-driven cases cover protocol bounds, command lifecycle/TTL, and malformed evidence; end-to-end branch/merge tests cover announced and stealth branches, nested branch merges, provenance preservation across `branchUuids`, unrelated-history and unaccepted-source refusals, and crash recovery; a reference model checks generated write sequences, conditional refusals, historical views, replay/restart, and access isolation, and proptest generates random scripts over that same model and shrinks a failure to the shortest script that still reproduces it. The model represents a concurrent same-slot merge as the *set* of candidate values with exact facet heads, so it asserts the read is one of the candidates rather than guessing Automerge's tie-break; a failure found this way pinned that a write retires the signatures it observed at its base (§6). All delivery permutations of dependent changes assert that readable signature entries have their introducing changes and bindings after save/load. Repository/runtime integration enforces the structural and cryptographic guarded-workflow rows above; node-authority authentication remains the explicit gap in §3. **Benchmarks: NOT RUN.** Dmeta size, hydration, signing and verification overhead for many one-field `blobPin` facets, frequent small updates, and long histories remain to be measured. Whole-value traversal can cost time even when reconciliation emits no operations. Sedimentree object-size caps do not bound cumulative history or verification cost; a resource-limit refusal is not forgery.
