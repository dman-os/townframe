# ADR 059: Web components

**Status:** Accepted (operator, 2026-11-26), except question 7 of section 5 (the external-page embedding API), which stays open and holds layer 7. Proposed by the claytxt lane. Nothing here is built.

**Amends:** [ADR 032](032-shell-micro-and-component-kit.md) (a mount is a registered element),
`docs/design-language/styling-contract.md` (`data-part` becomes `part`; how layers attach to a root),
[ADR 057](057-kit-baseline-and-the-identity-sheet.md) (the identity sheet's selectors),
[ADR 058](058-the-navigation-rack.md) (the rack is the first slotted element).

Related: `docs/scratch/web-components-step2.md` (the 11-24 design note this settles),
`docs/scratch/clay-pr-ledger.md` ("Web components: embrace fully, soon"), the Dioxus fork's interpreter
(`packages/interpreter/src/ts/core.ts`), `src/clay_dioxus/lib.rs` (`ShadowMount`), `src/clay_surface/render.rs`
(the wire vocabulary).

## 1. Context

The operator's direction (2026-11-19, re-raised 2026-11-26): we end up fully on web components, custom elements, shadow
DOM, `part`/`::part` and slots, with our own enhancements on top, sooner than later. Our enhancement is the layered,
adopted stylesheet stack: a shadow root hides the document's sheets, so we adopt ours into every root in a known
cascade order, which a plain web component cannot do.

Step 1 landed (stack layer 07): every micro, wasm guest or built-in, mounts through one shadow mount. What it is:

- `ShadowMount` renders `div[data-dioxus-shadow][data-dioxus-shadow-sheet="<css>"]`. The fork's interpreter sees the
  mark, calls `attachShadow({mode: "open"})`, moves the element's children into the root, and adopts two constructable
  sheets: the one shared `@layer host { ... }` flattening of the document's sheets, and the micro's own sheet (the
  attribute's text, unlayered). The end user's theme is appended to that same text as `@layer user { ... }`, per mount.
- No custom element is registered anywhere. Nothing outside Dioxus can host a micro, and a Solid, React or plain-HTML
  page cannot embed one.
- Kit parts are `data-part="..."` attributes in light DOM inside a root. Nothing is a real `part`.
- A nested micro (the shell hosting a panel) is a `ComponentMount` inside the parent's Dioxus tree, so its root is a
  shadow root inside the parent's shadow root; the nesting is visible only to the host.
- The wire (`clay_surface`) admits custom-element tags (inert, the host has no definition for them), the `slot`
  attribute and the `<slot>` tag, any `data-*` name, and no `part`, `exportparts`, `is` or `template`.
- Blitz has neither shadow roots nor custom elements. It takes the light-DOM path (`LightDomStylesheets`) and stays a
  fallback.
- New this week: intxt's web app renders our components under dioxus-ssr with no browser. A shadow mount has no
  serialised form there.

Decisions already on record that this ADR builds on (ledger, 11-24/25): the sandbox is wasm plus the host-checked wire,
not shadow DOM; scoped registries; host-generated tag names per binding, requested by the manifest-local binding name
(no NSID); a sanitized `setHTML`-like op; built-in micros isomorphic with wasm ones; never block on Blitz.

## 2. Decision

### 2.1 Elements: one generated tag per binding

A mount is a custom element. The tag is **generated by the host for each binding**; a guest never chooses one.

- A micro asks for a binding by its **manifest-local name** (ADR 050: `diff`, `rack`), never an NSID. The host resolves
  it to a presentation and returns the mount; the wire's mount node (`ComponentRef`) is what carries it today, so no
  guest-writable tag is involved.
- The tag is `ct-<slug>-<h>`: `<slug>` is the binding name lowercased and reduced to `[a-z0-9-]`, and `<h>` is eight hex
  characters of a hash of the owner's actor path (`micros/<cartridge>/<micro>`, ADR 052) and the binding name. It is
  deterministic: the SSR output of §2.6 and the live page must agree on a tag with no coordination, and a reload must
  not rename it. Two micros binding the same name get different tags, so a single global registry never collides.
- All generated tags share one class, `CtMount`, defined in the fork's interpreter bundle. The interpreter defines a tag
  lazily, the first time it creates an element whose name starts with the reserved prefix `ct-`, so the host emits no
  registration call and the same markup works in Wry, the web build and any page that loads the bundle. A binding gets
  its own subclass only when it needs behaviour of its own; none does today. The tag is the binding's identity in the
  DOM and the unit of the scope below.
- **Scoped registries.** The registry belongs to the mounting scope: a micro's root sees the definitions of its own
  bindings, not another micro's. Where the engine has scoped `CustomElementRegistry` (`attachShadow({customElementRegistry})`),
  each mount's root gets its own, holding its bindings' tags. Where it does not, the single global registry holds the
  deterministic tags above and a root simply never emits a tag outside its own bindings, which the host guarantees
  because it generates the tags. The contract is identical either way, so scoped registries are an isolation hardening
  we use when present, never a feature the page must have. Whether Wry's WebKitGTK and Android's WebView have them is measured in
  layer 3 (decided), not assumed.
- **Guest-written tags.** The wire keeps admitting custom-element tags (they stay inert), but refuses the reserved
  `ct-` prefix, so a guest cannot spell a host-defined element. See §2.7.

### 2.2 Attributes and properties

Rule: an attribute is a string a stylesheet or the markup itself may need to see; a property is a value only script
sets.

- **Attributes (serialisable, selectable, present in SSR):** `slot`, `hidden`, the state of the mount (`data-state`,
  mirroring what a part carries, §2.3), and the sheet attribute `data-ct-sheet` (§2.5). The mount's *identity* is the
  tag, so there is no `micro=` or `presentation=` attribute: nothing needs to read one and SSR already emits the tag.
- **Properties (typed, never serialised):** the props of a presentation, when it has any. Today a presentation takes none
  (ADR 032 first slice: a details presentation asks the shell which row is open through a call), and ADR 050 §9 defers
  props on views. Step 2 adds none. When props arrive they are a property per prop, set by the host, validated against
  the manifest's declared type at the boundary, and the capability prop is checked by the host (micro embed contract).
  A prop is never an attribute, so the wire carries no stringly-typed props and SSR output never has to render one.
- **Reflecting:** the element reflects nothing back from the guest. State flows host-to-element only, so the element is
  never a second source of truth for the micro's state.
- **Lifecycle belongs to Dioxus, not the element.** A mount's session is created and dropped by the Dioxus component
  (`MountedComponent`: `use_hook`, `use_drop`), which is the RAII shutdown the Clay design settled. The element's
  `connectedCallback` and `disconnectedCallback` therefore do not start or stop a micro in a Dioxus-rendered tree; they
  only attach the shadow root and adopt sheets. The one place they drive mount and unmount is the externally hosted
  element of §2.8, where there is no Dioxus component above it.

### 2.3 `part`, `exportparts`, and what the CSS becomes

`data-part="x"` becomes `part="x"`.

- **Names are qualified by component.** `::part()` is flat per shadow root, and `data-part="tab"` was unique only within
  a component (the styling contract's rule). The token is therefore `<component>-<part>`, with the component being the
  root class without `ct-`: `part="tabs-tab"`, `part="button-label"`, `part="shell-sidebar"`. A micro's own parts use its
  root class the same way. The headless modules already know their component name, so the rename is mechanical and a
  lint can check it (a `part` token begins with the root class's name).
- **State is a second token, not a selector.** `::part()` takes pseudo-classes but no attribute selectors, so the
  `data-state` that kit skins select cannot be selected from outside a root. The one enumerated state of a part is
  mirrored as a token `state-<v>`: `part="tabs-tab state-active"`, selected `::part(tabs-tab state-active)`. Native
  states keep their pseudo-classes (`:hover`, `:focus-visible`, `:disabled`). Every other axis is mirrored the same way
  (`data-variant`, `data-size`, `data-status`, `data-orientation` become `variant-<v>`, `size-<v>`, `status-<v>`,
  `orientation-<v>`), so an outside theme can select any of them; boolean axes keep a bare `data-*` and a native
  pseudo-class where one exists. `data-state` and the other `data-*` axes stay, because ARIA mirroring and the in-root skins read it.
- **Inside a root, plain selectors.** The kit and identity sheets are adopted into every root, so they keep ordinary
  selectors, with one mechanical substitution: `.ct-tabs [data-part="tab"]` becomes `.ct-tabs [part~="tabs-tab"]`.
  A `~=` attribute match works in a shadow root and in Blitz's light DOM alike, so one stylesheet serves both and
  Blitz stays a fallback without shaping the contract. The rule "a skin selector is a root class, a part and a state,
  never a tag or a position" stands; the `data-part` spelling in it changes.
- **From outside, `::part()`.** A page theming a micro from its own stylesheet writes `ct-diff-1a2b3c4d::part(tabs-tab
  state-active) { ... }`. That needs no `@layer user` injection and works for a micro embedded in a page that never
  loads our theme machinery.
- **`exportparts` through nested mounts.** A part crosses one shadow boundary only if the host element exports it, and
  a nested mount sits behind the parent's root, so every mount element the host renders carries `exportparts`. The
  host sets it; a guest cannot (§2.7). What it lists:
  - the kit's closed vocabulary, unprefixed, generated from the headless modules' part lists at build time, so
    `::part(tabs-tab)` from the top document reaches every kit tab at any nesting depth;
  - a micro's own parts, which the manifest declares explicitly (a new member of the view endpoint, `parts: [...]`), so a
    part that is not declared is not themeable from outside. The host prefixes each declared part with the binding name
    automatically (`exportparts="tab:diff-tab"`), so two nested micros can never collide.
- **What the injected theme still does.** Our `@layer user` enhancement reaches inside a root with any selector
  (`:root` tokens, descendants, `[data-state]` axes, tag-less combinators), which `::part()` cannot. Both stay: `::part`
  is the standard door for a foreign page, the injected stack is the powerful door for the app and its end user. Neither
  replaces the other. Decided: the user layer keeps full injection power (end-user styling is meant to be Obsidian-grade),
  and `::part` is an addition, not a narrowing.

### 2.4 Slots for nesting micros

Two kinds of nesting exist and they take different forms.

- **A mount inside another micro's content is just an element.** The parent's tree holds a generated-tag element; that
  element's own shadow root holds the child. No slot is needed and none is used: a Dioxus `ComponentMount` already
  yields exactly this shape.
- **A slot is for content the parent supplies to a frame.** A presentation that is a frame with holes (the shell's list
  and details positions, a sheet, the rack's cluster of ADR 058) declares `<slot name="...">` in its own tree; the parent
  puts what fills each hole as light children carrying `slot="..."`. The child owns its root and its layout; the parent
  owns what goes in.
- **The interpreter's child rule changes.** Today every child of a shadow host is moved into its root, so a host's light
  DOM is always empty and a slot can never be filled. The rule becomes: a child that carries a `slot` attribute stays
  in the host's light DOM; every other child is shadow content. A default-slot child is written `slot=""`. Events from
  slotted content bubble through the slot to the host as the platform defines, and the one document-level listener the
  interpreter already uses sees them through `composedPath()` (the root is open for that reason).
- Slotted light children are Dioxus nodes of the *parent's* tree, so the parent's signals and event handlers keep
  working with no wire crossing, and the child cannot read them (a slot assigns nodes for rendering; it does not hand the
  child a reference).
- **Over the wire.** A guest reaches a slot through the existing `slot` attribute on its own elements inside a mount
  node's children, and a guest's own `<slot>` is live only in a root that has light children, which only a host-rendered
  frame has. The wire needs no new node kind (§2.7).
- **Accessibility.** Slotting preserves the accessibility tree. `id` references (`aria-labelledby`, `for`,
  `aria-controls`) do not cross a shadow boundary, so a parent cannot label something inside a child; the kit keeps its
  referenced pairs inside one root, and a case that needs to cross takes the slot route.

### 2.5 How the layered sheets attach to each element's shadow root

The element, not an interpreter attribute hook, owns this. On connect (or on upgrade of a server-rendered element,
§2.6) a `CtMount` calls `attachShadow({mode: "open"})` and sets `adoptedStyleSheets` to an ordered list of
constructable sheets, in this order:

1. the **host sheet**: today's flattened document sheets as `@layer host { ... }` (tailwind, reset, tokens, kit,
   identity arrive as `host.*` sublayers, unchanged);
2. the **stack sheets**, one shared constructable sheet per entry of the ordered stylesheet stack (shipped, installed,
   the user's own: the 11-25 decision), each in its own layer, in stack order;
3. the **mount's own sheet**, the sanitized text a guest produced, in its own `@layer micro`.

Two changes from today follow.

- **Shared, not per mount.** Today the theme is appended as text to every mount's own sheet, so a theme of N kilobytes is
  stored in N attributes and parsed N times. The stack sheets are shared by reference like the host sheet, rebuilt once
  with `replaceSync`, and restyle every root at once. `UserStylesheet` stops flowing through `ShadowMount`; it is the stack
  the interpreter reads. This is the performance fix the design debt note asked for.
- **The mount's own sheet text still arrives as an attribute**, `data-ct-sheet`, because a Dioxus renderer can write
  attributes and has no op for "set a property on a node". The element observes the attribute
  (`attributeChangedCallback`) and `replaceSync`s its one own sheet, so a changed sheet restyles without recreating the
  root. A constructable sheet is not an inline `<style>`, so the web shell's CSP (`style-src-elem 'self'`) still holds.
  `use_mount_stylesheet`'s write-during-render is replaced by the element's connected callback reading the attribute;
  that retires the design debt recorded at layer 07.

The micro's own sheet moving from unlayered to `@layer micro`, below the stack, follows the 11-25 decision ("all above a
micro's own sheet"). It reverses today's "a micro's unlayered rules outrank `user`", which the theme lab uses to preview
a draft theme. Decided: that reversal lands with the stylesheet-stack work, not with the element layer, so the theme lab's draft
preview keeps working until the lab has a stack entry for its draft; the attachment above is the same either way.

### 2.6 Declarative shadow DOM for dioxus-ssr

The same mount renders to HTML with the same generated tag and a declarative shadow root:

```html
<ct-diff-1a2b3c4d>
  <template shadowrootmode="open">
    <style>@layer host, user; @import url("/assets/kit.css") layer(host);</style>
    <style>@layer micro { /* the mount's sanitized sheet */ }</style>
    ...the micro's content...
  </template>
  ...slotted light children, if any...
</ct-diff-1a2b3c4d>
```

- **Sheets are inline, the shared bundle is a link.** A declarative root cannot adopt constructable sheets, so it
  carries `<style>` elements. The kit bundle is one `@import ... layer(host)` of the bundle's URL, not an inlined copy,
  so N mounts on a page share one fetched and cached resource. The stack sheets are the same `@import`s in stack order,
  each in its own layer. The page's CSP governs this form and is the embedder's (a static SSR page can allow its own
  `style-src`); the web shell's live CSP is untouched, since it never takes the SSR path.
- **One renderer, three outputs.** The mount component emits the element in the browser and Wry (adopted sheets), the
  declarative root under dioxus-ssr (`<template shadowrootmode>`, inline styles), and plain light DOM under Blitz.
  A host context says which; `LightDomStylesheets` generalises to a small `MountRendering` enum, and there is one
  `ShadowMount`, not three.
- **Upgrade, not replacement.** When `CtMount` is defined over an element that already has a declarative root, its
  constructor finds `this.shadowRoot` and adopts into it instead of calling `attachShadow` (which would throw), and
  replaces the `<style>` elements with the shared adopted sheets once defined. Without JavaScript the declarative root
  alone renders correctly, which is what a read-only viewer needs.
- **No hydration in this ADR.** Decided: static declarative output first; hydration only if intxt asks. Making the Dioxus
  web renderer hydrate into an existing shadow root is a separate piece of work.
- **Engine support.** Declarative shadow DOM parses in current Chromium, Firefox and Safari (Chrome 111, Safari 16.4,
  Firefox 123) and in the WebKitGTK and Android WebView builds we ship; each is confirmed by the layer that builds the
  output, in a real page, not assumed.

### 2.7 What the wire and admission (`clay_surface`) must admit

By reading the current admission code (not yet pinned by a test, which the first layer adds first):

- **A hole to close first.** `static_attribute` interns any `data-*` name, including `data-dioxus-shadow` and
  `data-dioxus-shadow-sheet`. A guest can therefore mark its own element as a shadow host and hand the interpreter an
  unsanitized sheet text, bypassing `sanitize_stylesheet` and the no-egress rule (a `url()` in an adopted sheet fetches).
  Admission must refuse the reserved `data-dioxus-*` and `data-ct-*` names, and the reserved `ct-` tag prefix. Both are
  refusals with the same fault shape as any unknown attribute. This is needed by step 1 as shipped, independent of the
  rest of this ADR, and is the first layer.
- **`part` is admitted** on any element: a space-separated token list, each token `[a-z0-9-]+`, bounded count and
  length. A guest uses it for its own parts and the host exports what the manifest declares (§2.3).
- **`exportparts` is not admitted from a guest.** The host writes it on mount elements. A guest's own custom-element
  tags (still inert) therefore export nothing.
- **`slot` and `<slot>` stay admitted unchanged.** `template`, `shadowrootmode`, `is`, `shadowrootdelegatesfocus` and
  `<script>`-adjacent tags stay out: a guest never writes a shadow root of its own. Declarative shadow DOM is a host
  serialisation of the host's own mounts only.
- **The stylesheet sanitizer admits `::part()`, `::slotted()` and `:host`** and needs no new rule: it re-emits selectors
  untouched and removes only what fetches. A guest's own sheet may style the parts of its own children and the slotted
  nodes of its own root. The host's `exportparts` decides what a parent can reach.
- **A `setHTML`-like op** (the 11-25 decision) is a separate admission surface and is not changed here: it returns a
  sanitized subtree into a guest's own root, never into the host document.

### 2.8 Other frameworks host a micro

**Open (question 7, the operator's product call); layer 7 waits.** The sketch below is one of two options; the other is
that the embedder talks to a node over a socket and names the micro directly, with the host checking capabilities there
and no resolver in the page. What the options share: the page loads the interpreter's element bundle and writes an
element; they differ in who resolves a binding and who the capability check trusts.

Option A, a page-defined resolver. A Solid, React or plain-HTML page embeds a micro by loading the interpreter's element bundle and writing the host's
element for the binding. The page is a host, so it supplies the binding table: the bundle exposes `CtMount` as an
unregistered base class and a small `ct.define(tag, resolver)`; the page defines its own tag with its own resolver, which
turns the element into a node client (the connected and disconnected callbacks then do start and stop the mount,
§2.2). The kit's vocabulary and the stylesheet stack reach the page's mounts the same way they reach ours. Writing this
embedding and rendering a micro in Solid under it is the cross-framework test the ledger has held open since 11-06.

### 2.9 Kit components stay light DOM

Decided: kit components (`Button`, `Tabs`, `Card`, ...) are not custom elements. They are plain Dioxus inside a root, because
light DOM is cheaper, keeps Dioxus diffing every part individually, and the contract already carries their vocabulary as
attributes that any framework can emit. Parts of a kit component are `part` attributes inside the mount's root, exported
through `exportparts` (§2.3). Turning one into an element later changes the tag the DOM shows and nothing in the
vocabulary; that waits until a non-Dioxus page needs `<ct-button>` on its own, and there is no `<ct-button>` before
there is a consumer.

## 3. Consequences

- **Positive:** nothing outside Dioxus could host a micro, and now any page can; a foreign page themes a micro with
  `::part()` and no part of our machinery; nested micros are isolated by the platform, not by a convention; the SSR
  viewer gets styled, isolated, JavaScript-free output; the per-mount theme duplication goes.
- **Positive:** the kit's CSS is one sheet for shadow roots and Blitz's light DOM (`[part~=...]`).
- **Cost:** the part rename touches every headless module (55 sites), every kit and identity sheet and micro sheet
  (about 180 selectors in the kit alone), the daytxt_web Playwright and Bombadil selectors and the per-component docs and
  tests. Unmerged code takes no shim: the rename is one commit per layer, not a dual spelling.
- **Cost:** the fork's interpreter gains a custom element class, a light/shadow child rule and a stack-sheet registry,
  all TypeScript in a fork we own; each is a bump of the fork rev, which the layers batch.
- **Cost:** `::part()` is a flat namespace per root, which is why part names are component-qualified and why state is a
  token; both are visible in the markup.
- **Risk:** shadow roots across `id` references and focus (§2.4) bite any kit component that references across a mount
  boundary; no such component exists, and a lint on kit headless modules would catch the first.
- **Risk:** the Dioxus fork's SSR path for `<template>` content and a `shadowrootmode` attribute is untested; the DSD
  layer begins with a render test through a headless browser rather than a string compare.

## 4. Order of work

One draft PR per layer (stack layers 111 and up), each verified in the real Wry desktop app under Xvfb on
mothership-alpha, not only in the web build; Cargo tests and clippy narrow and on alpha.

1. **Close the admission hole** (§2.7): a failing test first (a guest sets `data-dioxus-shadow-sheet` with a `url()`),
   then the reserved-name refusals (`data-dioxus-*`, `data-ct-*`, the `ct-` tag prefix, a guest `exportparts`, and any
   other interpreter-reserved attribute the audit finds). It is based directly on the elevation layer so it can be cut
   to main on its own, and `part` is admitted in layer 2, not here. `clay_surface` only.
2. **`part` rename** (§2.3): `part` admitted on the wire; qualified tokens in the kit's headless modules and the micros, `[part~=...]` in every kit,
   identity and micro sheet, the `state-<v>` token, the lint for the qualification, the Playwright and Bombadil
   selectors, the styling contract amended. No custom element yet.
3. **The element** (§2.1, §2.5): `CtMount` and the generated tags (deterministic hash, `ct-` prefix) in the fork, the
   `data-ct-sheet` attribute, the shared stack sheets replacing per-mount theme text, `use_mount_stylesheet` out of
   render, scoped registries when the engine has them (measure first on Wry and Android). The fork's old
   `data-dioxus-shadow` hook is removed for Dioxus hosts and kept for nothing: Pierre's own shadow host (`diffs-container`)
   moves to the element.
4. **Declarative shadow DOM** (§2.6): the `MountRendering` split, the SSR form, a Playwright page that loads the string
   with no script and then with the bundle, the upgrade path. Moves ahead of layer 3 if intxt needs it first (it works on
   any host tag).
5. **`exportparts` and outside theming** (§2.3): the kit's generated vocabulary, the manifest's `parts` member, a page
   theming a nested micro with `::part()` and nothing else.
6. **Slots** (§2.4): the interpreter's light/shadow child rule, the shell's list and details frames and ADR 058's rack as
   the first slotted presentations, event and focus tests on Wry.
7. **External hosting** (§2.8): the unregistered base class and `ct.define`, a plain-HTML page and a Solid page
   embedding one micro, the cross-framework test.

## 5. Design questions and their answers

Answered by the operator on 2026-11-26, except question 7.

1. **Scoped registries on our engines.** Measured in layer 3; the design works without them (§2.1).
2. **The user layer.** Keeps full injection power; `::part` is an addition (§2.3).
3. **The other axes.** Every axis is mirrored as a part token (§2.3).
4. **Part qualification.** Component-qualified (`tabs-tab`); the theme vocabulary is renamed outright, with no back-compat
   because nothing is on main.
5. **What a micro exports.** An explicit manifest `parts` member; the host prefixes each with the binding name (§2.3).
6. **The micro's own sheet below the stack.** Lands with the stylesheet-stack work, not layer 3 (§2.5).
7. **OPEN: the external page's embedding API (§2.8).** Option A, a page-defined resolver (`ct.define(tag, resolver)`);
   option B, the embedder talks to a node over a socket and names the micro directly. A product question about who may
   embed what and how a foreign page proves capabilities to the host. Layer 7 waits.
8. **Hydration.** Static DSD first; hydration only if intxt asks.
9. **Kit components as elements.** Light DOM inside roots; no `<ct-button>` until there is a consumer (§2.9).
10. **Order of work.** As written in §4, unless intxt reports being blocked on DSD, in which case DSD moves to second.
