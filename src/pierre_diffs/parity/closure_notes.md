### CodeView (`components/CodeView.ts`; scoping pass C0, C1 and C2 ported)

Why: the diffshub viewer runs `CodeView` and shows no blank area on a fast scrollbar jump. The mechanism is the combination of (1) the rendered slice living in a `position: sticky` container (`stickyContainer`, `applyStickyPositioning`) inside a `container` whose height is the full (paged) scroll height and a `stickyOffset` spacer above it, so the compositor keeps the stale slice glued to the viewport until the next render moves the spacer; (2) `fitPerfectly` on far jumps (render only the viewport plus one gap and header, then queue a second render for the overscan); (3) an element pool of `diffs-container` shells; (4) a computed layout (`VirtualFileMetrics` through `updateCodeViewLayout`) reconciled by measurement (`reconcileRenderedItems`, a `ResizeObserver` on the sticky container) and scroll anchors; (5) a paged scroll / rebase scheme (`ScrollRebaseConfig`) for content taller than browsers allow. Host-trait analysis. Everything CodeView does against the platform, grouped, with where it lands.

1. Structural edits (the model, `Document`, no new host trait). `createElement` for `container`, `stickyContainer`, `stickyOffset`, pooled `diffs-container` shells and header/footer hosts; `appendChild`, `prepend`, `before`, `after`, `remove`, `replaceChildren`/`textContent = ''`, `firstChild`, `nextSibling`, `childNodes.length`, `contains`, `hasAttribute`/`setAttribute`/`tabIndex` (`tabindex` on the root: it must be focusable for the `keydown` listener), `shadowRoot.children` and `child.remove()` (`cleanElement`), `instanceof SVGElement` (`isPooledShadowChild`: tag test on the node). `Document` has `create_element`, `append_child`, `insert_before`, `remove`, `replace_children`, `children`, `child_nodes`, `is_attached`, `shadow_root`, attribute and style accessors; it lacks `prepend`, `before`, `after`, `first_child` and `next_sibling` (all derivable from `insert_before`/`child_nodes`/`next_sibling_element`; add two or three small methods rather than helpers in CodeView).
2. Style writes (the model, `set_style_property`/`remove_style_property`). root `overflow-anchor: none`; `container`: `contain: layout style`, `margin-top`/`margin-bottom`, `height`; `stickyOffset`: `contain: layout size`, `height`; `stickyContainer`: `position: sticky`, `width: 100%`, `contain: layout style inline-size`, `isolation: isolate`, `display: flex`, `flex-direction: column`, `gap`, `top`, `bottom`, `pointer-events`, and the custom property `--diffs-overflow-override`; header/footer host `display: flow-root`. No counterpart is missing: the scroller nodes are ordinary `Document` nodes the renderer already flattens. Two consequences. (a) `top`, `bottom` and the spacer `height` are written on every scrolled frame (`applyStickyPositioning`), so each frame is a Document edit that makes Dioxus re-render the scroller subtree; the renderer's keyed pass over a full slice must be cheap enough per frame (measure in C6; an edit-class filter or a style-only path in the renderer is the likely answer). (b) `position: sticky`, `contain`, `isolation` and `overflow-anchor` must reach the webview as written; the renderer must not drop style properties it does not know.
3. Geometry reads (host trait, answered from the geometry cache). `root.scrollTop` (`getScrollTop`), `root.getBoundingClientRect().height` (`getHeight`), `ResizeObserverEntry.borderBoxSize[0].blockSize` for the sticky container and header/footer hosts (`handleResize`), `getBoundingClientRect().height` of header/footer hosts right after mounting (`measureMountedHosts`: a synchronous read of a node that has not been laid out; no counterpart, the cache answers "unmeasured" and the `onresize` event delivers the height one dispatch later, which `handleResize`'s host branch already handles), `getBoundingClientRect().height` of items and the sticky container (dev validators: DROP). `VirtualizerHost` already has `element_scroll_top`, `element_bounding_height`; CodeView needs only those two plus the resize entries; reuse them (`CodeViewHost: VirtualizerHost`-style supertrait pieces rather than a copy).
4. Platform reads with no current counterpart (new `CodeViewHost` methods, answered by the embedder): `window.devicePixelRatio` (`roundToDevicePixel`, called on every scroll write and settle check; fractional ratios change results, so a constant 1 is wrong on HiDPI), `matchMedia('(prefers-reduced-motion: reduce)')` (`prefersReducedMotion`), `performance.now()` (the default timestamp of `computeRenderRangeAndEmit` and `scrollTo`'s animation start; the frame timestamps rAF hands over are the same clock, so the host defines one `now()` and the frame queue passes it), `navigator.userAgent`/`platform`/`maxTouchPoints` (`isFirefox()` at field initialisation, `MOBILE_SAFARI` once at module load: `PlatformInfo` exists in `utils/dom/platform.rs` but lacks `max_touch_points`; both become instance values from the host), `Math.random()` (the sticky jitter in `applyStickyPositioning`: `top`/`bottom` are offset by a random number of line heights so a lagging slice during a fast scrollbar drag does not line up exactly with the new one; keep it, but through a host `random()` so the oracle can replay a seeded sequence), `document.activeElement` and `shadowRoot.activeElement` (`renderedItemOwnsFocus`; the Dioxus host has to track focus from `focusin`/`focusout` and answer "does this node or a descendant own focus").
5. Platform writes. `root.scrollTo({ top, behavior: 'instant' })` (`applyScrollFix`): `VirtualizerHost::element_scroll_to` exists; the Dioxus implementation is an async `MountedData::scroll`, so a `scroll` event with the pre-write position can arrive after the write. `applyScrollFix` already records the written value in `this.scrollTop` and clears `scrollDirty`, which is what makes an asynchronous write tolerable, but `handleScroll` marks `scrollDirty` again and reads the cache: a stale event can pull the logical scroll top back for one frame (C6 risk; the Virtualizer's `spawn_scroll` already hit the same class of problem). `root.focus({ preventScroll: true })` (`fixContainerFocus`): no counterpart; `MountedData::set_focus` takes no `preventScroll`, which needs checking (C4/C6).
6. Observers and listeners. One `ResizeObserver` over `stickyContainer`, `root`, `header.element`, `footer.element`, with `observe`, `unobserve` (header/footer teardown) and `disconnect` (`cleanUp`): `VirtualizerHost::observe_resize` has no `unobserve`; add `observe_resize`/`unobserve_resize`/`disconnect_resize` to the CodeView host. Root listeners `scroll`, `wheel`, `touchstart`, `pointerdown`, `keydown`, all passive: Dioxus handlers on the scroller root; `add_element_scroll_listener` exists, the four user-input ones are new and collapse to one host call (`clearPendingScroll` takes no event). Parity risk: a scrollbar drag raises `pointerdown` on the root in Chromium, which is what upstream relies on to cancel a programmatic scroll; other webviews may not.
7. Timers and frames. `setTimeout(restoreScrollInteractions, 120)`/`clearTimeout` (`ScrollSyncHost::set_timeout`/`clear_timeout` exist and the Dioxus host implements them over the embedder's `sleep`). `queueRender`/`dequeueRender` (the ported `UniversalRenderingManager` over `AnimationFrames`). A smooth `scrollTo` re-queues a render every frame until the spring settles, so it needs a real frame cadence: the Dioxus host's frames are event-driven ("one dispatch is one frame") with a spawned tick for a callback that queues again; that tick must be paced (about 16 ms), or a smooth scroll runs as fast as the executor spins. `computeSpringStep` is closed form in `dt`, so any cadence is correct, only smoothness changes.
8. No counterpart, no port: `console.error` (unknown ids in `updateItem`, `updateItemId`, `removeItem`: the methods return `false`, the port keeps the return and drops the log) and `console.warn` (unresolved scroll targets: `scrollTo` returns), `window.__INSTANCE`/`__TOGGLE`, `CodeView.__STOP`, the `DIFFS_DEVELOPMENT_BUILD` validators.

Design points beyond the host table.

1. Async geometry versus the same-frame reads. Upstream measures in the frame that rendered: `reconcileRenderedItems(updatedItems)` calls `instance.reconcileHeights()` straight after `flushManagers`, and `measureMountedHosts` reads host heights in the same read phase. Dioxus delivers geometry after layout, so on the first frame after a render the cache answers "unmeasured" (the line estimate, as `geometry.rs` already does) and the real heights arrive through `onresize`, which reaches `handleResize`'s sticky-container branch (the `|blockSize - stickyHeight| >= 1` test triggers `reconcileRenderedItems()`, `updateStickyPositioning()` and an anchored scroll fix). That path exists upstream for annotation and wrapping changes, so the logic is covered; what changes is that it carries every measurement, one dispatch late. This is the same trade S12b made for the simple virtualizer. The sticky container is what keeps the late measurement from showing: stale rows stay on screen while it settles.
2. Per-item options. Upstream hands every `VirtualizedFileDiff` an options object whose getters read the live `CodeView` options (`this.options[key]`), plus per-item state (`collapsed` from the item, callbacks wrapped with the item context). The Rust `FileDiff` owns its `FileDiffOptions`. Recommended: CodeView builds the item's `FileDiffOptions` from its current options and the item and pushes it to the instance through a crate-internal `set_options_from_code_view` that skips `setOptions`'s advanced-mode throw and its `resetLayoutCache`/`instanceChanged` side effects (CodeView owns those through `pendingLayoutReset` and `renderOptionsRevision`), at exactly the two places upstream reads options lazily: before `updateCodeViewLayout` (layout reads `collapsed`, `diffStyle`, `disableFileHeader`, ...) and before `render` when `renderedOptionsRevision` differs. Callback wrappers (one `Rc<dyn Fn>` per callback key per item, reading CodeView's current callback through a `Weak` at call time) are built once per item, not per push. Cost: one struct clone per item per option change, which `markLayoutDirtyFromIndex(0)` already pays in O(items).
3. Pool ownership. Upstream leaves the sprite and the theme and unsafe-CSS `style` elements in the pooled shell's shadow root (`isPooledShadowChild`) and the next instance adopts them; the Rust `FileDiff` owns and frees them on `clean_up` (closure notes, 2c handoff), which defeats the pool's purpose. C4 has to move shell assets to the container's ownership (the instance adopts existing sprite and style nodes by attribute, as upstream's `getOrCreate*` do), which touches `file_diff/nodes.rs`/`theme.rs`, the churn tests and the S12b oracle's "oracle removes them after cleanUp" note. The pool also needs the arena discipline the model already has: an element the pool declines (`queueElementForPool` over the limit, a stale generation, `invalidateElementPool`, `clearElementPool`, `cleanUp`) must be `discard`ed, since `Document` frees by owner, not by GC; `elementPoolTracker`'s `WeakMap` becomes a `HashMap<NodeKey, u64>` pruned on discard. `pendingElementPool` and `isComponentManaged` exist only for React's portal cleanup; the Dioxus view passes no `request_owner_render` (the annotation wrappers are model nodes), so `isComponentManaged` is false and the second-phase pool is dead code (Q5).
4. `instanceChanged` is annotated upstream as "technically broken" (`NOTE(amadeus)`: it should collect changed instances and recompute all tops); the port inherits it as is.
5. `resolveAlignedScrollPosition` carries `REVIEW: lets turn this into a named interface object`; the Rust struct for its arguments is the natural resolution and not a divergence.

(2) `capture_pending_layout_anchor` returns before `getScrollAnchor` while there is no root and `todo!`s past it; C3 fills `getScrollAnchor`/`getScrollAnchorViewportTop`/`resolveAnchoredScrollTop` over the `ScrollAnchor` type that exists, and `reconcile_items` already passes it the next id map. (3) `PendingScrollTarget` carries the target plus its `PendingAlign` (`nearest` resolved), and `rename_pending_scroll_target` is done; `normalizeScrollTarget` builds it. (4) Use `round_to_device_pixel(value, host.device_pixel_ratio())` and `host.prefers_reduced_motion()`; the frame timestamp default (`performance.now()`) is a host read C3/C5 add (`CodeViewHost::now`). (5) The harness to copy: `oracle/s12c_code_view.mjs` runs the published class over a bare `document`, replaces `render` on the instance with a recorder, calls private methods directly, and `components/code_view/oracle_tests.rs` replays it over `FakeDom` (the `recompute` step is the layout half of `computeRenderRangeAndEmit`; C5 replaces it with the real render). Tests: `items_upstream_tests.rs` (removeItem 3, updateItemId 1 of 2 plus a Rust-only retarget test, collapsed 6, all their model halves; the render halves are C5, divergences.psv) and Rust-only tests of the arms no case reaches; the oracle (`s12c_code_view.json`: 198 scenarios, 3,348 steps; every earlier golden is byte-identical). Not covered by the oracle: the callbacks' missing `context` argument, the shared (non-selection) callback wrappers firing (only their installation is exercised by `onLineClick`/`header`/`footer` identity in `setOptions`), `capturePendingLayoutAnchor` past its guard, and anything with a root. Open question for the operator (not decided here): should the user callbacks carry an item context argument as upstream's do (`CodeViewDiffItemContext`)? The port omits it (a closure captures its id); adding it means one callback type per key.
